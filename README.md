# Strait Pay — P2P-обмен USDT ⇄ RUB в Telegram

aiogram 3 · PostgreSQL · USDT в сети TON (собственные кошельки, Toncenter API, tonutils).

## Запуск
```bash
cp .env.example .env            # заполнить BOT_TOKEN, ADMIN_IDS, TON_SEED (python -m bot.services.ton seed)
docker compose up -d db         # или свой PostgreSQL в DATABASE_URL
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m bot
```
Схема БД: ограничения `balance >= 0` и `frozen >= 0` на уровне PostgreSQL, составные индексы под частые
запросы (сделки покупателя и продавца по статусу, журнал пользователя, алерты); тест `test_migrated_schema_equals_fresh_schema`
сверяет колонки, индексы и CHECK-ограничения свежей и мигрированной базы.
При старте бот применяет версионные миграции PostgreSQL (`bot/models.py: MIGRATIONS`, таблица
`schema_version`), затем создаёт недостающие новые таблицы. Существующая БД обновляется явными `ALTER`.
На одну БД допускается **один процесс** бота (pg advisory lock): второй экземпляр завершится с ошибкой.
Состояние диалога хранится в БД (`fsm_state`) и переживает рестарт; в процессе держится его копия, поэтому
чтение состояния не ходит в БД. PDF, присланный во время неоплаченной сделки без активного шага, всё равно
примется как чек. Пул PostgreSQL: 10+20 соединений, `lock_timeout` 15 с — ожидание блокировки не вешает бота.

## Тесты
```bash
.venv/bin/python -m pytest -q                       # SQLite
# полный набор, включая гонки SELECT FOR UPDATE и миграцию старой схемы, на одноразовой PostgreSQL:
P2P_TEST_PG=postgresql+asyncpg://p2p@127.0.0.1:5432/p2p_test .venv/bin/python -m pytest -q
```
Тестовая БД из `P2P_TEST_PG` **полностью очищается** (DROP SCHEMA public) — не указывайте рабочую.

## Кошелёк: USDT в сети TON — свои кошельки, без посредников
Все деньги — USDT (USD₮, jetton `TON_USDT_MASTER`) в сети TON на кошельках самого бота (`bot/services/ton.py`).
xRocket полностью убран.

**Ключи.** Все кошельки (wallet v4r2) выводятся из одного секрета: ключ = HMAC-SHA256(`TON_SEED`, метка). В БД —
только адреса. `TON_SEED` (64 hex) — в `.env`: `python -m bot.services.ton seed` создаёт новый, `python -m
bot.services.ton address` печатает адрес горячего кошелька. **Храните копию офлайн**: без него средства не достать,
с ним их может вывести кто угодно. Пустой `TON_SEED` = кошелёк выключен (пополнение и вывод недоступны).
- `gas` — **горячий кошелёк** («адрес для пополнения газа»): TON на все комиссии + USDT для выплат. Метка прежняя,
  поэтому адрес тот же, что был у газ-кошелька раньше (при том же `TON_SEED`).
- `deposit:<id>` — **личный адрес пополнения** пользователя, постоянный (тот же, что был в старой TON-версии).
- `debt:<id>` — **личный адрес оператора для погашения долга**: всё, что пришло, гасит долг без комиссии, сверх
  долга — на баланс.

**Toncenter.** Чтение — Toncenter v3 (индексатор: jetton-переводы и балансы) и v2 `getWalletInformation`
(seqno и баланс TON прямо с лайтсервера, ошибки никогда не превращаются в «пустой кошелёк»); подпись и отправка —
tonutils. Ключ API (@tonapibot, 10 запросов/с вместо 1) владелец ставит в «Админ-панель → TON-кошелёк → Ключ
Toncenter»: бот проверяет его запросом, сообщение с ключом удаляет, ключ перекрывает `TON_API_KEY` из `.env`
(«-» — вернуть ключ из `.env`). `TON_TESTNET=true` — тестовая сеть (тогда задайте и `TON_USDT_MASTER` тестнета).

**Пополнение.** «Кошелёк → Пополнить» показывает личный адрес (кнопка копирования). Цикл (раз в 20 с) читает
входящие USD₮-переводы на все личные адреса (`/api/v3/jetton/transfers`, курсор + 10 мин перекрытия на задержку
индексатора) и зачисляет каждый **ровно один раз** по хешу транзакции (`deposits.tx_hash` UNIQUE): только настоящий
USD₮ (jetton master сверяется), только не `aborted`, только после выдачи адреса. Минус `deposit_fee` (1,5%) — доход
площадки. Меньше `deposit_min` — запись `small`, не зачисляется (защита от пыли). Пользователь получает уведомление с
кнопкой «Транзакция» (tonviewer), админ-чат — карточку с суммой, отправителем и хешем. «Проверить поступление» —
сканирование адресов пользователя сразу.

**Сбор на горячий кошелёк.** Когда на личном адресе набралось `ton_sweep_min` (5 USDT): горячий кошелёк шлёт
0,1 TON газа → адрес переводит весь USDT на горячий кошелёк (сдача TON возвращается). Зачисление на баланс от сбора не
зависит. Не собранное видно в «TON-кошельке» и в «Финансах».

**Вывод.** «Кошелёк → Вывести»: адрес TON (UQ…/EQ…; адреса бота не принимаются; «Как в прошлый раз») → memo для
биржи → сумма → подтверждение. Комиссия `withdraw_pct` (1,5%) + `chain_withdraw_fee` (1 USDT, покрывает газ),
минимум `chain_withdraw_min`. Сумма списывается сразу, вывод встаёт в очередь (`queued`) и будит цикл: **хватает
USDT и TON на горячем кошельке — уходит сразу**, не хватает — ждёт строго по порядку (большой не обгоняют
маленькие), админам — алерт с адресом для пополнения. Пока по выводу не подписано ни одного сообщения, его можно
отменить. Готово — уведомление с хешем и ссылкой, комиссия — в доход площадки.

**Никогда не дважды.** Каждое сообщение кошелька — строка `ton_transfers` (seqno, valid_until = +60 с, хеш),
она **коммитится до отправки в сеть**; у кошелька одно сообщение в пути. Исполнено ⇔ seqno кошелька вырос;
не исполнено до valid_until + 2 мин — «мертво» навсегда, и только тогда вывод подписывается снова (тем же seqno).
Перед каждым новым сообщением seqno сети сверяется с записями: если «мёртвое» сообщение всё же исполнено, оно
восстанавливается, а поверх ничего не подписывается. Jetton-перевод несёт `query_id` = id записи — перевод в сети
сопоставляется с выводом точно. `aborted` в сети (USDT не ушли) → ещё 2 попытки, затем возврат. Исполнено, но
перевод не виден 30 мин → вывод `unknown`, деньги удержаны, повтора нет: владелец проверяет в Tonviewer и решает в
карточке («Подтвердить выполнение» / «Вернуть средства», с повторным подтверждением). Чужое сообщение кошелька
(seqno ушёл дальше записей) → алерт «ключ мог утечь».

**Переход с xRocket.** Миграция 19 добавляет `deposits.tx_hash/source`, `withdrawals.transfer_id`; при старте
невыплаченные xRocket-выводы из очереди возвращаются на баланс (пользователь получает сообщение), открытые счета
закрываются, по выводам с неизвестным итогом и счетам владельцам приходит один алерт — проверить в приложении
xRocket и решить в карточке вывода. Токен xRocket удаляется из настроек. История xRocket остаётся в БД.

## Вход по заявке
`signup_review = 1` (по умолчанию; «Настройки → Правила и лог-чат»): новый пользователь не видит бота, пока его не
впустят. Анкета: **кто вы** (P2P-продавец / покупатель) → **оборот в день** (кнопкой или своей суммой) → продавец
прикладывает **скриншот баланса или оборота** → «Проверьте заявку» → «Отправить заявку». Заявка (со скриншотом)
публикуется в лог-чате в ветке **«📝 Заявки на вход»** с кнопками «Одобрить» / «Отклонить» прямо под ней (нет лог-чата —
админам в личку); она же — в «Админ-панель → Заявки на вход» (там ещё «Отклонить с причиной» и «Показать скриншот»).
Одобрили — пользователю приходит приветствие с кнопкой **«Открыть главное меню»**; отклонили — причина, новая
заявка через 24 ч. Карточка в ветке после решения меняется: кто решил и когда, кнопки убираются. Ссылка тимлида
работает сразу — пользователь попадает в команду ещё до решения. Пока не впустили, любое сообщение и любая кнопка
возвращают к анкете (`handlers/signup.py`, фильтр на роутере). Все, кто был в боте до обновления, впущены
(миграция 15: `users.access`, таблица `signups`). `signup_review = 0` — бот открыт всем, никто не ждёт.

## Чат сделки
На экране сделки — «Чат сделки»: покупатель, мерчант и оператор Bybit-ордера пишут в одну ленту, каждое сообщение
приходит остальным с кнопкой «Ответить в чат», вся переписка видна на экране чата (последние сообщения, экран
остаётся с баннером). Ссылки и @юзернеймы не проходят (по тексту и по разметке Telegram) — отправитель видит
предупреждение, админам уходит алерт. Администрация открывает чат из своей карточки сделки и может писать (ей
ссылки можно). Чужие пользователи в чат не попадают; лимит — 30 сообщений в час. Режим чата заканчивается любой
другой кнопкой: случайный текст потом в чат не уйдёт. Личное сообщение («Администрации», «Написать лично») осталось.

## Сообщения через бота
Кнопка «Написать» на экране сделки: покупатель, мерчант и оператор пишут друг другу и администрации; администратор —
кому угодно (из карточки сделки или профиля). Сообщение приходит с кнопкой **«Ответить»**, переписка идёт в боте и
попадает в историю сделки (её видно в лог-чате). **Ссылки и @юзернеймы запрещены** (кроме администрации): такое
сообщение не отправляется, админам уходит алерт. Не больше 30 сообщений в час от пользователя.

## Strait Pay API для сервисов
Полная документация: [docs/API.md](docs/API.md), она же отдаётся по `GET /docs`. Канон бренда: [docs/BRAND.md](docs/BRAND.md).
- Доступ по заявке: бот → «Strait Pay API» (`/api`) → анкета (проект, ссылка, трафик, оборот) → админ одобряет или
  отклоняет с причиной в «Админ-панель → API для сервисов» → пользователь выпускает токен (показывается один раз,
  в БД только SHA-256), задаёт вебхук и берёт секрет подписи.
- Заказ по API — обычная сделка, где покупатель — владелец токена (`deals.api_client_id`). У заказов свои лимиты
  (сумма, сутки, число неоплаченных, запросов в секунду) вместо ограничений для частного покупателя. USDT по
  успешному заказу идут на баланс владельца на обычных условиях. Личное меню, «Мои сделки» и уведомления
  владельца API-заказами не засоряются: о смене статуса сообщают вебхуки (outbox `api_events`, подпись
  HMAC-SHA256, повторы до суток, только публичные https-адреса).
- Чек по API проверяется по содержимому (PDF), копия уходит владельцу токена в чат — так Telegram выдаёт file_id,
  дальше чек идёт продавцу тем же путём, что и из бота.
- Запуск: `API_ENABLED=true`, `API_HOST`/`API_PORT` (по умолчанию 127.0.0.1:8080), наружу — через HTTPS-прокси на
  вашем домене, `API_PUBLIC_URL=https://api.<домен>`.

## Покупатель: несколько сделок сразу, менеджер, отмена пополнения
- Покупатель ведёт несколько покупок одновременно: до `buyer_max_open` (5) неоплаченных (с чеком — не считаются);
  меню показывает до трёх открытых сделок кнопками, «RUB ⇄ USDT» — список открытых и сразу ввод новой суммы.
  Сверх предела — «У вас уже N неоплаченных сделок». Фото/PDF без шага ввода прикрепляется к сделке, только если
  неоплаченная одна.
- `manager` — ник менеджера: кнопка «Вопросы менеджеру» в меню, в «Помощи» и команда `/manager` (нет менеджера —
  ник поддержки).
- Меню «/»: Главное меню, Купить USDT за рубли, Продать USDT на свою карту, Кошелёк, Мои сделки, Помощь и условия,
  Связаться с менеджером; админам ещё Админ-панель, Поиск, Сделка по номеру. Остальные команды работают, но не в меню.
- Пополнение можно отменить («Отменить» на экране пополнения). Отменённое сутки ещё проверяется: если человек всё же
  оплатил, деньги зачислятся.

## Покупатели и плательщики API: брошенные сделки
Сделка, истёкшая без чека, — брошенная: она держала карту продавца и его USDT. `abandon_limit` (3) брошенных за
сутки — пауза `abandon_pause_minutes` (120) после последней; отмены по-прежнему без ограничений. API: заказ
принимает `payer_id` — ID клиента сервиса, который платит; то же правило работает по каждому плательщику
отдельно (`429 payer_paused`), а админ в карточке сделки может «не принимать» заказы этого плательщика
(`api_payer_blocks`, `403 payer_blocked`). Остальные клиенты сервиса не затрагиваются.

## Несколько сделок на карту, заявка сначала лучшим
- По одной карте идёт до `card_parallel` (3) сделок сразу; суммы на карте различаются хотя бы на 1 ₽ — продавец
  отличает переводы по сумме. Карта «занята» только когда сделок столько, сколько можно; реквизиты карты не
  меняются, пока по ней идёт хоть одна сделка.
- Новую ордерную заявку первые `order_wave_seconds` (45 с) видят только `order_first_wave` (5) лучших мерчантов
  (репутация + опыт), затем — все и чаты. 0 — всем сразу.
- Чек покупателя по Bybit-ордеру приходит оператору с кнопками (подтвердить / спор) и мерчанту — копией без кнопок,
  с напоминанием отпустить USDT. Чат сделки — тройной: покупатель, мерчант, оператор; каждое сообщение подписано
  «Пишет: …» и «вы здесь — …». Для API-заказа покупатель — сервис, в чате только мерчант и оператор.

## Управление деньгами: /balance и ручные инструменты
- `/balance` — балансы и правка (модуль `handlers/admin_balance.py`, см. его описание в истории коммитов).
- Долг оператора: «Долг: +» (получил USDT мимо бота) и «Долг: −» (вернул мимо бота) — с причиной, в журнал, оператору
  уведомление. Кнопки в карточке баланса и оператора.
- Карта: админ меняет минимум, максимум, лимит в день (те же проверки, что у владельца, владелец уведомлён) и
  ставит карту в поток (только если хватает баланса).
- Спор по Bybit-ордеру: «Покупателю, но USDT оператору не пришли» — покупатель получает USDT, а долг оператору не
  начисляется (мерчант не отпустил USDT — убыток площадки, разбирайтесь с мерчантом).

## Защита площадки
- Предел долга оператора `operator_max_debt` (1000 USDT): долг плюс ордера в работе; сверх — новые ордера не
  принимаются до погашения.
- Снятый или забаненный оператор: его ордера без реквизитов уходят другим операторам с обычным сроком, сделки с
  выданными реквизитами без оплаты закрываются (покупатель ещё может загрузить поздний чек — сделка уйдёт
  администрации). «Закрыть сделку» оператором тоже оставляет окно для позднего чека.
- Сделка у оператора без таймера не висит молча: через час без чека — напоминание оператору, через 6 ч — алерт.

## Карты в потоке: только с балансом
Карту можно включить, только если её максимум и свободный баланс мерчанта покрывают сделку от `card_min_rub`
(2 000 ₽). Новая карта без баланса сохраняется выключенной с причиной. Задача `cards_flow` (раз в минуту) снимает с
потока карты, чей владелец ушёл ниже порога, и пишет ему причину. Причина видна в списке карт и в приложении.

## Чек: несколько неоплаченных сделок
PDF без нажатия «Прикрепить» при нескольких неоплаченных сделках не теряется: бот проверяет файл, запоминает его и
спрашивает «К какой сделке этот чек?». PDF до выдачи реквизитов — «чек пока не нужен, не переводите».

## Мини-приложение
Telegram Mini App на том же сервере, что API и инструкции: `/app` (страница, `bot/webapp/`) и `/app/api/*`
(`bot/api/webapp.py` — аккаунт, сделки, кошелёк, карты; `bot/api/webapp_roles.py` — мерчант, оператор, админ,
споры, файлы, аватар, лог страницы). Вход — подпись Telegram `initData` (бот-токен, не старше 24 ч), те же правила:
бан, вход по заявке, сообщество. **Каждое действие — та же функция, что у кнопки бота** (`handlers.orders`,
`handlers.deal`, `handlers.admin`): одни правила, те же уведомления сторонам и тот же журнал.

Вкладки: **Главная** (баланс, быстрые действия, «Нужно действие», работа по ролям) · **Обмен** (купить USDT за рубли
с живым расчётом; «Продать» — своя карта или реквизиты под сумму) · **Сделки** (активные/завершённые, фильтр по
роли) · **Работа** (карты и смена, ордерные реквизиты, оператор, администрирование, статистика) · **Профиль**
(аватар из Telegram, роли, уведомления без звука, помощь).
- **Сделка**: сумма и «пролив» — линия хода сделки, таймер, реквизиты с копированием, вкладка **Чат** (покупатель,
  мерчант, оператор и администрация; быстрые ответы, счётчик непрочитанных), действия внизу экрана: чек (PDF),
  подтверждение, **спор с файлами** (видео/выписка до 10 МБ — сохраняются через чат с ботом), доказательства, отмена.
- **Ордерный мерчант**: кабинет (статус, репутация, курс, доход, время на оплату по умолчанию), свободные заявки →
  «Взять»: через Bybit-ордер (ссылка) или с баланса (реквизиты карта/СБП + время на оплату), «Отказаться».
- **Оператор**: свободные Bybit-ордера → «Принять ордер», реквизиты из ордера, «Другой мерчант» / «Нет реквизитов» /
  «Пересоздать» / «Закрыть», подтверждение оплаты, **оценка мерчанта 1–10**, долг: погашение с баланса и личный адрес TON.
- **Админ**: стол (споры, «продавец молчит», открытые сделки, выводы на проверке, деньги, горячий кошелёк), все
  сделки с поиском по номеру/ID, в сделке — участники, материалы спора (фото и видео прямо в приложении, PDF — в чат
  с ботом) и **решение** с комментарием (те же вердикты, что в боте).
- Надёжность: у каждого запроса таймаут (чтение — с одним повтором), устаревший ответ для уже покинутого экрана
  отбрасывается, экран обновляется опросом только при изменениях и не трогает поле ввода; ошибки страницы уходят в
  лог бота (тема «Ошибки бота»). CSP разрешает только свои скрипты, Telegram и маяк Cloudflare.
- Дизайн: светлый, плоский — тонкие линии вместо теней, один акцент (морская зелень — покупка/подтверждение,
  красный — продажа/риск), Golos Text + IBM Plex Mono для реквизитов и адресов, скелетоны при загрузке, шторки снизу.
- Адрес: настройка `webapp_url`; пусто — домен `docs_url` + `/app` (`https://straitpay.best/app`). Нужен
  `API_ENABLED=true` и HTTPS-прокси на домен — то же, что для `/docs`.
- Бот сам ставит кнопку «Strait Pay» у поля ввода (меню) и обновляет её при смене адреса; кнопки «Открыть
  приложение» (последняя в главном меню), «Кошелёк в приложении», «Карты в приложении», «В приложении» (сделка), «Чат в приложении».
- В лог-чате у сделки — «Сделка в приложении» (t.me-ссылка): `webapp_link` или Main Mini App бота, если он включён
  в BotFather (Bot Settings → Configure Mini App → URL `https://straitpay.best/app`).

## Заявки в чате: живой статус
Пост заявки в общем чате и чате команды — живая карточка: сумма, банк, курс; пока мерчант не найден — «Ищем
мерчанта» и кнопка «Взять». Дальше кнопка пропадает, а блок «Ход заявки» отмечает шаги ✅ / ⏳ / ▫️: мерчант взял
заявку → ссылка на Bybit-ордер получена (ждём до HH:MM) → оператор выдал реквизиты (ждём оператора / проверяет
ордер) → покупатель оплатил (ждём перевод и чек) → оплата подтверждена (чек на проверке); спор отдельной строкой.
Итог — «Выполнена» / «Отменена» / «Истекла». Мерчант отказался — пост снова «Ищем мерчанта» с кнопкой. Реквизиты в
чат не попадают никогда. Посты правит задача `chat_posts` (каждые 5 с, только при изменении текста) и закрытие
предложений.

## Вывод только прокрученного
`withdraw_turnover=1` (по умолчанию). У пользователя `deposit_lock` — пополнения, ещё не прокрученные в сделках:
каждое зачисленное пополнение увеличивает его, USDT, ушедшие покупателям в завершённых сделках (и погашение долга
оператора с баланса), уменьшают. **Можно вывести = баланс − deposit_lock** (не меньше 0). Купленные USDT, доход
тимлида и начисления админа выводятся сразу. Проверка — на вводе суммы, на подтверждении и окончательно под
блокировкой строки перед списанием. «Кошелёк» и экраны вывода показывают, сколько можно вывести и сколько ещё
прокрутить; админ видит это в карточке пользователя и может «Снять ограничение вывода» (в журнал и «Действия
админов»). API: `withdrawable` в `/v1/balance` и `withdrawable_usdt` в `/v1/me`. Старые пользователи начинают с 0.

## Очередь выводов и финансы
**TON-кошелёк в админке** («Админ-панель → TON-кошелёк»): статус сети, ключ Toncenter (только последние символы и
откуда он), **адрес горячего кошелька** (копирование, Tonviewer) с балансами TON (газ) и USDT, не собранное на
личных адресах, очередь выводов списком с нехваткой средств, выводы в пути и на проверке, «Запустить цикл сейчас».
Только владельцам: «Ключ Toncenter» и «Вывести с кошелька» (USDT или TON на свой адрес — с подсказкой, сколько можно
забрать без денег пользователей, резерв газа не трогается). У пользователя в «Кошельке» видно место каждого вывода в
очереди и сумму перед ним.

- **Выводы ждут, а не отклоняются.** Не хватает USDT (или TON на газ) на горячем кошельке — вывод принят и списан,
  цикл каждые 20 с отправляет очередь **строго по порядку**, как только хватает (маленький не обгоняет большой).
  Пока по выводу не подписано ни одного сообщения, пользователь может его отменить. Админам — алерт раз в час:
  сколько ждёт и адрес для пополнения; газа меньше 1 TON — отдельный алерт.
- **Финансы** («Админ-панель → Финансы» и живое сообщение в ветке «📊 Статистика и финансы», обновляется раз в 10
  мин): что есть (USDT горячего кошелька минус отправленное, + не собранное на личных адресах; газ в TON), что
  должны пользователям (балансы, заморозка в сделках, выводы в пути), **сколько можно забрать** = есть − должны
  (прибыль уже внутри), прибыль за 24 ч / 7 / 30 дней / всё время, оборот, очередь выводов с подсказкой, на сколько
  пополнить горячий кошелёк.

## Деньги
`usdt = rub / курс`; с продавца замораживается `usdt·(1−%продавца)`, покупатель получает `usdt·(1−%площадки)`,
разница — доход площадки. Пример 10 000 ₽ / 100 / 5% / 6% → 95 / 94 / 1. Всё меняется в админке.

Процент мерчанта со **статичной картой** — `seller_pct` (по умолчанию 5%, бывает личный), не больше процента
площадки. **Ордерные мерчанты работают без процента, по фиксированному курсу** `order_rate` (по умолчанию 104 ₽):
мерчант отдаёт `сумма / order_rate` USDT, покупатель получает как обычно, разница — площадке. 10 400 ₽ по ордеру →
мерчант отдаёт 100 USDT, покупатель получает 97,76, площадке 2,24. `order_rate` не может быть выше
`rate / (1 − platform_pct)` — иначе площадка доплачивала бы покупателю; бот не даст сохранить такой курс, в том числе
при снижении `rate` (сначала снизьте курс ордерного). Условия фиксируются в сделке при её создании.

**Личные условия покупателя.** Профиль пользователя → «Условия покупателя»: свой курс и/или процент (как у
API-клиента). Действуют на все его покупки — по картам и ордерным реквизитам; сторона мерчанта не меняется, разница —
площадке; сделка, где площадка ушла бы в минус, не создаётся. Покупатель видит «ваши условия» на экранах покупки.

**Тимлиды.** С каждой завершённой сделки, где мерчант — участник команды (не сам тимлид), тимлид получает
`team_pct` (1%) от суммы сделки в USDT по её курсу (10 400 ₽ / 100 → 1,04 USDT) на баланс. Платит площадка из своего
дохода по сделке и не больше него; в сделке это `team_id` / `team_fee`, в журнале — `team_fee`.

**API-клиенты — свои условия.** У подключения по API можно задать курс и процент («Админ-панель → API-клиенты →
клиент → Курс клиента / Процент клиента», «-» — общие). Они одинаковы для всех его заказов — и по статичным картам,
и по ордерным реквизитам: курс 100 и 7% → с 10 000 ₽ клиент получает 93 USDT. Сторона мерчанта не меняется
(процент карты / курс ордерного), разница — площадке; экран клиента показывает маржу для карты и для ордера, а
заказ, где площадка ушла бы в минус, не создаётся. `GET /v1/rates` отдаёт клиенту его условия.

**Управление — «Админ-панель → Комиссии и проценты»**: все ставки на одном экране (что платит покупатель,
процент мерчанта по карте, фиксированный курс ордерного мерчанта и его потолок, маржа площадки, комиссии пополнения
и выводов — процент и фикс, процент тимлида, списки личных ставок мерчантов и условий покупателей, пример на 10 000 ₽), каждая меняется кнопкой, после сохранения экран возвращается сюда же. **Личный
процент** (только статичная карта): профиль пользователя → «Процент мерчанта», «Сбросить на общую». Действует для
новых сделок; выше ставки покупателя не применяется, даже если процент площадки потом снизят. Изменение приходит
мерчанту уведомлением, уходит в лог-чат и журнал действий. Личных ставок для ордеров нет (миграция 12 удаляет
`users.pct_order`).

## Сделки: сроки и споры
- `deal_minutes` — время на перевод и PDF-чек. Чек, загруженный после срока (в пределах `late_minutes`),
  снова замораживает средства продавца и возвращает сделку ему на проверку; если у продавца уже нет средств,
  чек уходит администрации.
- Через `confirm_minutes` после чека продавцу приходит напоминание, а покупатель может открыть спор.
  Через `escalate_minutes` спор открывается автоматически.
- В споре обе стороны добавляют доказательства (видео, фото, PDF, текст). Решение админа — только после
  экрана подтверждения с суммами для каждой стороны.
- Экран сделки показывает этап (1 — перевод и чек, 2 — проверка поступления, 3 — зачисление) и кнопки
  «Скопировать номер/телефон» и «Скопировать сумму». Перед отменой покупатель видит, сколько отмен у него осталось.
- Решение по спору админ может сопроводить комментарием (5–500 символов): он хранится в `deals.resolution`,
  приходит обеим сторонам и виден на экране сделки. Списки споров показывают, сколько прошло с момента чека.
- Ограничений на число сделок и отмен у покупателя нет; одновременно — одна открытая сделка (её экран, чек и
  таймер — текущий шаг покупателя). Лимиты API-клиентов — свои, в «API-клиенты».

## Администрирование
- **Панель** («Админ-панель», `/admin` — и в личке, и прямо в админ-чате): роль (владелец / админ); «Требует
  внимания» по пунктам (заявки на вход, споры, выводы на проверке, ордера без оператора, обращения, анкеты, заявки
  на команды и API…) с кнопкой на каждую очередь; «За 24 часа» (сделки, доход, новые пользователи); «Люди» (на
  смене, карты, ордерные мерчанты, операторы, команды, админы); «Деньги» (балансы, горячий кошелёк TON и газ, долг операторов);
  «Админ-чат» (подключён ли, есть ли темы). Разделы парами: Найти · Сделки, Ввод и вывод · Карты, Ордерные
  мерчанты · Операторы, Команды · API-клиенты, Комиссии · Настройки, Чат и рассылка · Обращения,
  Администраторы · Журнал, Отчёты CSV · Заявки на вход. История любой операции показывает последние события (длинная — обрезается сверху).
- **Сделка по номеру**: `/deal 15`, «Найти» → `#15` или «Открыть» на карточке в лог-чате (в заголовке карточки —
  `/deal N`). Карточка: кто создал (покупатель), кто принял (мерчант), оператор — с @username и числом сделок;
  деньги, реквизиты, сроки, чек и спор, последние события. **Управление**: «Выдать реквизиты самому» (для заявки:
  админ становится её оператором, мерчант снимается и его заморозка возвращается; рубли — на реквизиты админа, долга
  нет), «Изменить сумму» (пересчёт по условиям сделки, заморозка мерчанта следует за суммой), «Продлить +15 мин»,
  «Закрыть заявку» / «Отменить сделку», «Завершить: USDT покупателю», «Отменить: в пользу продавца», написать
  любому участнику.
- **Профиль**: роли (оператор, ордерный мерчант, тимлид, участник команды), долг оператора, личные условия; кнопки
  «Процент мерчанта», «Условия покупателя», «Оператор: долг и ордера».
- **Профиль по Telegram ID.** «Найти»: ID, `@username`, `#15` (сделка), `в482` (вывод), `п12` (пополнение),
  номер карты/телефона. Поиск по выводу/пополнению открывает профиль владельца с кнопкой на операцию.
  В профиле — доступно/заморожено, покупки и продажи отдельно (объём, отмены по причинам), споры,
  пополнено/выведено; кнопки «Сделки», «Операции», «Карты», «Споры», «Выводы и пополнения», «Изменить баланс».
- **Корректировка баланса**: начислить/списать → сумма → причина из списка («Другое» — с комментарием) →
  черновик `Корректировка #N` в БД с балансом «до → после» → «Подтвердить». Повторное нажатие и рестарт бота
  ничего не меняют. Списывается только доступный баланс; замороженное меняется только через сделки.
  Ledger получает запись `adj:N` с причиной; действие пишется в журнал и уходит алертом.
  `adjust_approval_usdt` > 0 — от этой суммы нужен второй администратор (по умолчанию выключено).
- **Карточки операций**: вывод (списано, к отправке, комиссия, адрес и memo, каждое сообщение кошелька: seqno,
  статус, хеш; следующее действие, «Проверить в сети», «Транзакция», «История вывода»), пополнение (адрес,
  отправитель, хеш, ссылка), сделка/спор, корректировка, обращение. Вывод `unknown` решает только владелец, с
  повторным подтверждением.
- **Журнал событий и алерты (outbox).** Событие сохраняется в таблицу `events` в той же транзакции, что и
  изменение; отправку в лог-чат выполняет фоновая задача и повторяет её при сбое Telegram (до часа; недоставленные
  видны на панели). В чат уходит живая карточка операции (см. «Админ-чат») с кнопкой «Подробнее» — полные
  реквизиты и файлы только в полной карточке. Алерты: вывод `unknown`, отклонённый сетью перевод и возврат, нехватка USDT/газа на горячем кошельке, новый спор и
  автоэскалация, недоставленные уведомления продавцу, корректировки, бан пользователя/карты, ошибки сверки
  (не чаще раза в час на операцию), обращения. Штатные операции — только в истории и сводке.
- **Обращения** пользователей со статусами «ждёт ответа / отвечено / закрыто»; ответ из карточки.
- **Настройки** разбиты на разделы (курс и комиссии, сроки, кошелёк, правила, тексты); значения показаны
  с единицами, у параметра видно значение по умолчанию и формат ввода, после сохранения — «было → стало».
  Баланс горячего кошелька на панели кэшируется на 60 с (перед выплатой всегда запрашивается заново).
- **Отчёты CSV** за 1/7/30 дней: сделки, журнал операций (`delta` и `frozen_delta`), пополнения и выводы.
- **Ledger**: `delta` — изменение доступно+заморожено, `frozen_delta` — изменение заморозки; заморозка и
  разморозка по сделкам журналируются. «Операции» в профиле сверяют журнал с балансом.
- **Админ-чат = лог-чат.** Кнопка, нажатая в группе, правит то самое сообщение прямо в группе — в личку
  ничего не приходит. Карточка лога по «Подробнее» превращается в полный экран (сделка, пользователь, команда…)
  на месте, «Свернуть в карточку» возвращает лог. Команды и ответы на вопросы бота (сумма, причина отказа,
  поиск) админ пишет прямо в теме: его сообщение-ответ удаляется, результат — правкой того же экрана. Файлы
  (чек, доказательства спора, скриншот заявки, CSV) приходят в ту же тему. Кнопки и команды работают только для
  администраторов: чужой клик — «Только для администраторов.», чужие команды — тишина.
- **Ссылки вместо кнопок.** Люди и номера в логах и карточках — ссылки `t.me/<бот>?start=a-<вид>-<id>`
  (`a-user-123`, `a-deal-15`, `a-team-3`, `a-wd-7`, `a-om-…`, `a-apa-…`, `a-signup-…`): клик открывает карточку
  в личке с ботом (только для админов; остальным — обычное меню).
- **Администраторы.** Владельцы — `ADMIN_IDS` в .env (их права не снимаются). Админов назначают и снимают только
  владельцы: «Админ-панель → Администраторы», кнопка «Сделать админом» в карточке пользователя или команды
  `/addadmin ID|@ник`, `/deladmin ID|@ник`. Список хранится в БД (переживает рестарт). Новый админ получает
  сообщение с кнопкой «Админ-панель», одноразовую ссылку в админ-чат и меню команд админа; снятого бот удаляет
  из админ-чата и возвращает обычное меню. Назначение и снятие — в «Действия админов».

## Ордерные реквизиты (реквизиты под сумму)
Покупатель нажимает «RUB ⇄ USDT» и просто отправляет сумму в рублях — без списков и фильтров. Бот сам выбирает
самую надёжную статичную карту под сумму (больше завершённых сделок), а если её нет — предлагает **заявку на
реквизиты под точную сумму** (`order_min_rub`–`order_max_rub`): «Создать заявку» → статус `searching`. Дальше:

1. **Рассылка.** Заявка уходит **каждому** одобренному ордерному мерчанту — без лимитов сумм и без «включить
   приём»: мерчант сам решает, брать или нет. В сообщении по пунктам: сумма перевода, банк покупателя, курс ордера,
   сумма ордера в USDT, сколько это по курсу сервиса и доход мерчанта, срок. Кнопки: «Взять · Bybit-ордер» (баланс не
   нужен) и «Взять · с баланса» (только если свободного USDT хватает). Та же заявка публикуется в чат сообщества и
   в чаты всех команд с кнопкой «Взять заявку в боте» (`t.me/<бот>?start=o<id>`, в чате команды
   `o<id>_t<команда>`): бот открывает заявку и те же две кнопки, не-мерчанту предлагает анкету. Раз в 20 с заявка
   досылается новым мерчантам и чатам; не доставленное (бот заблокирован) не повторяется. Некому отправить — алерт.
2. **Взятие** — кто первым нажал, тот и взял (блокировка строки сделки). «С баланса»: `seller_debit` мерчанта
   **замораживается**; «Bybit-ордер»: ничего не замораживается, дальше ссылка и оператор (см. ниже). Сделка →
   `assigned`, у остальных мерчантов и в чатах сообщение меняется на «уже взята».
3. **Реквизиты** (режим «Баланс»). Мерчант за `order_take_minutes` (10 мин) выдаёт реквизиты одним сообщением: номер карты
   или телефон СБП и банк (`2200 7001 2345 6781 Сбербанк`, `+7 900 123-45-67 Т-Банк`), ФИО по желанию второй
   строкой; тип определяется по номеру, «сбер», «тинькофф» и т. п. приводятся к названию банка. Старые карты не
   предлагаются. Так же выдаёт реквизиты оператор Bybit-ордера. Время на оплату выбирается кнопкой: от
   `order_pay_minutes` (15) до 60 мин. Реквизиты разовые: в общий список «Купить USDT» не попадают. Сделка → `waiting_payment`.
4. Дальше обычная сделка: покупатель переводит и присылает PDF → мерчант проверяет поступление → «Деньги пришли»
   (USDT покупателю, доход мерчанту) или спор. Работают автоспор, поздний чек, удержание залога и все решения админа.
5. **Таймауты.** Мерчант отказался или не выдал реквизиты вовремя → заморозка снимается, заявка возвращается в
   поиск, повторно этому мерчанту не приходит. Никто не взял за `order_search_minutes` (15) → заявка закрывается с
   причиной `no_merchant`, в лимит отмен покупателя это не засчитывается. Покупатель может отменить заявку до выдачи
   реквизитов (у мерчанта снимается заморозка).

**Ордерные мерчанты.** «Ордерные реквизиты → Заполнить анкету» (4 шага): откуда берёт реквизиты и ордера, как
быстро выдаёт, какие банки, о себе. Анкета уходит алертом в лог-чат и сообщением каждому админу. В «Админ-панель →
Ордерные мерчанты» её одобряют или отклоняют с причиной (подать снова — через 24 ч), там же приостанавливают и
возобновляют. Кабинет: «На линии: заявки приходят все», курс, свободный баланс и на какую заявку его хватит «с
баланса», заявки в работе, свободные заявки (открыть и взять), результаты, время на оплату по умолчанию. Лимитов,
тумблера приёма и режима больше нет (миграция 14 удаляет `min_rub`, `max_rub`, `max_open_rub`, `accepting`, `mode`).

**API.** `POST /v1/orders` без подходящей карты открывает ордерную заявку: ответ `202`, статус
`searching_requisites` → `merchant_assigned` → [`requisites_check`] → реквизиты придут вебхуком со статусом
`awaiting_payment`. В заказе есть `next_action` и `stage`, история статусов — `GET /v1/orders/{id}/history`,
ордерные мерчанты на смене — `order_requisites` в `GET /v1/liquidity`. Отключить: `"order_requisites": false`.

### Bybit-ордера и операторы
Нет статичной карты под сумму → заявка (из бота или `POST /v1/orders`, ответ 202) уходит всем ордерным мерчантам
и в чаты; первый нажавший «Взять» её получает и выбирает, как работать:
- **Bybit-ордер** — баланс в боте не нужен, ничего не замораживается. Мерчант присылает ссылку на ордер Bybit P2P
  (`https://…bybit.com/…`, одна ссылка — одна заявка) → статус `checking` → **каждому оператору** приходит сообщение
  по пунктам (сумма ордера, курс мерчанта, на сколько USDT зайти, банк покупателя, мерчант, срок) **без ссылки** и с
  кнопкой «Принять ордер». Первый принявший получает ссылку и экран выдачи реквизитов, у остальных сообщение
  меняется на «принял другой оператор». Оператор может «Вернуть другим» (ордер снова уходит всем операторам) или
  «Отклонить ссылку» (заявка возвращается мерчанту). Реквизиты из ордера уходят покупателю (в бот или вебхуком по
  API). Чек: оператору — с кнопками «Подтвердить» / «Спор», мерчанту — только PDF. Подтверждение зачисляет
  покупателю USDT **с баланса площадки**, а USDT ордера пришли оператору на Bybit — **это его долг** (см. ниже).
  Спор оператора: причина → видео из ЛК или выписка → решается сразу в его пользу (нет оплаты — отмена, другая
  сумма — проведение по факту). Ордер не принят / реквизиты не выданы за `order_check_minutes` (15 мин) — заявка
  закрывается (`no_merchant`), админам — алерт.
- **С баланса** — под заявку замораживаются `сумма / order_rate` USDT мерчанта, реквизиты выдаёт и оплату
  подтверждает он сам.

### Операторы и их долг
- **Кто оператор**: «Админ-панель → Операторы → Добавить оператора» (ID или @username; человек должен запустить
  бота), там же «Убрать из операторов». `OPERATOR_IDS` из `.env` тоже работают. Пока нет ни одного — операторы админы.
- **Долг**: каждое подтверждённое оператором Bybit-ордером (или решённое в пользу покупателя) добавляет к его долгу
  `seller_debit` — USDT ордера на его Bybit. Таблица `operators.debt`, история — события `op:<id>`.
- **Кабинет «Оператор»** (кнопка в меню): долг, ордера в работе, свободные ордера («Принять ордер»), результаты,
  «Погасить переводом USDT» — личный адрес погашения долга в сети TON (`ton_addresses.purpose = debt`, без
  комиссии; каждый перевод уменьшает долг, переплата идёт на баланс) и «Погасить с баланса». Админ может «Списать долг вручную».
- В «Финансах» и на панели — «Долг операторов»; в «можно забрать» он не входит, пока не погашен.

### Защита заявок: готовая карта, ссылка за 5 минут, сделка у оператора без таймеров
- «Взять · Bybit-ордер» сначала спрашивает **«Карта под ордер у вас уже готова?»**. «Нет, ещё ищу» — бот просит
  заявку не брать (можно взять с баланса, если хватает USDT). Берут только мерчанты с готовой картой.
- После взятия у мерчанта `order_link_minutes` (**5 мин**, старое значение 2 при запуске меняется на 5) на ссылку.
  Нет ссылки — заявка уходит другим, покупатель о взятии не узнаёт, а площадка сама ставит мерчанту оценку 3 в
  репутацию (`operator_id = 0`). Пока у мерчанта есть взятая Bybit-заявка без ссылки, вторую он взять не может.
- **Оператор принял ордер — таймеров больше нет**: ни на проверку, ни на оплату покупателем, автоспора по чеку
  тоже нет. Сделку ведёт оператор: выдаёт реквизиты, «**Пересоздать ордер**» (мерчант создаёт новый и присылает
  ссылку за 5 мин, она приходит тому же оператору; выданные реквизиты отзываются, покупателю — «не переводите»; не
  больше 3 раз, дальше — другой мерчант) и «**Закрыть сделку**» (до оплаты, с подтверждением). Без оператора ордер
  по-прежнему ждёт `order_check_minutes`.
- Оператор зашёл в ордер, а реквизитов нет: «В ордере нет реквизитов» → «Мерчант не дал реквизиты» — заявка
  уходит другим, мерчанту засчитывается **пропуск**.
- **Экран оператора — всё кнопками.** В сообщении о новом ордере: «Принять ордер» и «Найти другого мерчанта»
  (сразу, без принятия). Принятый ордер: «Открыть ордер Bybit», «Выдать реквизиты клиенту» (после неё —
  реквизиты одним сообщением), «Найти другого мерчанта», «Пересоздать ордер», «В ордере нет реквизитов»,
  «Вернуть операторам», «Закрыть сделку», «Чат сделки». Чек покупателя приходит оператору с кнопками «Оплата
  пришла — подтвердить» и «Оплаты нет — спор»; те же кнопки на экране сделки.
- Оператор не может принять ордер по своей же покупке (и мерчантскому ордеру): ему такой ордер не рассылается,
  «Принять» отвечает отказом. Кто проверяет оплату, тот всегда видит кнопки проверки.
- **Кабинет оператора** (`op`): сделки по группам — «Проверьте оплату», «Выдайте реквизиты», «Ждём перевод
  покупателя», «Мерчант пересоздаёт ордер», «Спор»; свободные ордера с «Принять»; долг и результаты. В главном
  меню — «Оператор · в работе N» и «Проверить оплату (N)» только по тем сделкам, где проверяет он сам.
- Статусы по-человечески: «Ищем мерчанта», «Ждём ссылку на Bybit-ордер», «Ждём оператора», «Оператор проверяет
  ордер», «Ждём перевод покупателя», «Оператор/продавец проверяет оплату» — в боте, в мини-приложении и в админке.
- `strike_limit` (3) пропусков **подряд** — пауза `strike_sleep_hours` (72 ч): заявки не приходят и не берутся,
  «Ордерный кабинет» показывает до какого времени. Выданные по ордеру реквизиты обнуляют счётчик. Админ видит
  пропуски и паузу в карточке мерчанта и пользователя и может снять их («Снять паузу и пропуски»).
- Операторы проходят «вход по заявке» и обязательное вступление в чат: оператор, добавленный в панели (или из
  `OPERATOR_IDS`), принимает ордера и подтверждает оплату, даже если сам заявку на вход не подавал; при назначении
  оператором пользователь сразу одобряется.
- «Проблема с ордером» → «Искать другого мерчанта · без пропуска» — другая причина, без штрафа. В обоих случаях
  этот мерчант больше не может взять эту заявку (отметка «отказался» по заявке, `take` его не пускает).
- **Репутация мерчанта**: после **завершения сделки** (а не при выдаче реквизитов) или передачи заявки другому
  оператор ставит оценку с фактами перед глазами (через сколько минут пришла ссылка, сколько раз пересоздавали);
  ранее: после выдачи реквизитов по Bybit-ордеру или передачи заявки другому оператор ставил
  мерчанту оценку 1–10 (`merchant_ratings`, одна на заявку). После `rep_min_count` (10) оценок репутация — среднее
  последних 30: ниже `rep_mid` (7) — Bybit-заявки только до `rep_mid_max_rub` (30 000 ₽), ниже `rep_low` (5) —
  только с баланса. Видна мерчанту в кабинете, операторам в заявке, админу в карточке мерчанта.
- Заявка мерчантам и в чаты: сумма, банк покупателя, **курс площадки для ордера** и **на сколько USDT зайти в
  ордер** — без «дохода мерчанта».
- **Лог операторов**: каждое действие — отдельный пост в теме «Операторы» админ-чата: принял ордер, выдал
  реквизиты, вернул, отклонил ссылку, «мерчант не дал реквизиты», время вышло, подтвердил оплату (и долг вырос).

### Команды и тимлиды
- «Команда» в меню → «Создать команду»: название и о себе → админ одобряет или отклоняет с причиной в
  «Админ-панель → Команды» (подать снова — через 24 ч), там же приостановка и личный процент тимлида.
- Одобренный тимлид получает реферальную ссылку `t.me/<бот>?start=t<id>`: кто запустит бота по ней (и ещё не в
  команде) — участник его команды и получает кнопку «Вступить в чат команды» (личная ссылка на один вход).
- Чат команды: тимлид добавляет бота админом группы (приглашать, закреплять) и пишет в ней `/team`. В чат приходят
  все ордерные заявки со ссылкой `?start=o<id>_t<команда>` — по ней можно и взять заявку, и попасть в команду.
- Тимлиду — `team_pct` (1%) от каждой сделки участника (см. «Деньги»). Кабинет тимлида: ссылка, участники, чат,
  доход сегодня / 7 дней / всего.
- **Командный баланс.** Процент тимлида начисляется на отдельный командный баланс (в журнале — `team_income`).
  «Команда» → «На основной баланс» переводит его на основной (`team_out` / `team_in`), оттуда — вывод в крипту.
  Командные балансы входят в «что должны пользователям» в финансах; сверка журнала в «Операциях» учитывает их.
- **Управление командой (админ).** «Админ-панель → Команды» (или `/teams`, `/team ID` в админ-чате): список
  со статусом, размером, тимлидом и чатом; карточка команды — тимлид, участники (список со ссылками), чат
  (название, число участников, id), реферальная ссылка, процент, оборот за 24 ч и всего, кто и когда одобрил.
  Кнопки: «Ссылка в чат команды» (личная одноразовая ссылка для админа на 1 ч — бот там админ), «Участники»,
  «Процент тимлида», «Приостановить / Возобновить», «Отключить чат». В карточке пользователя — «Убрать из
  команды»: снимает с команды и удаляет из её чата.
Статусы сделки: `searching` → `assigned` → [`checking`] → `waiting_payment` → `paid` → `completed` / `dispute`.


## Для продавцов (мерчантов)
- **Панель мерчанта** («Продать USDT»): статус смены, сегодняшний доход, карты с видимостью, «В работе (N)» —
  все открытые сделки (обычные и ордерные), где нужно действие — сверху; «Статистика», «Ордерные реквизиты»,
  «Настройки», «Пополнить».
- **Статистика и доход**: сегодня / 7 / 30 дней / всё время — сделки (ордерных отдельно), оборот, средний чек,
  доход, доля успешных, среднее время подтверждения, споры; доход по дням за неделю.
- **Настройки мерчанта**: уведомления о сделках и чеках со звуком или без (удобно ночью), выключить все карты.
- **Ордерный кабинет**: результаты по ордерам (сегодня, 7 дней, всего, успешность), лимиты, время на оплату по
  умолчанию; реквизиты — одно сообщение и «Выдать».
- В «Мои карты» — строка «Сегодня: N сделок на X ₽ · доход +Y USDT»; «Статистика продаж» — сегодня / 7 / 30 дней:
  сделки, оборот, доход, среднее время подтверждения, споры.
- За 5 мин до автозавершения смены приходит напоминание с кнопкой «Остаюсь на смене».
- **Повторный чек**: один и тот же файл (Telegram `file_unique_id`) в двух сделках — продавец видит
  предупреждение в уведомлении о чеке, админам уходит алерт. Чек, пришедший в ту же секунду, когда сделка
  истекла, не теряется — обрабатывается как поздний.
- Админу чек и доказательства спора приходят альбомами (фото/видео и документы по 10), пояснения сторон — одним
  сообщением.

## Структура
`bot/handlers`: `commands` (слэш-команды и deep link `/start o…/t…/om`), `start` (меню, помощь, поддержка),
`signup` (вход по заявке), `market` (покупка: сумма → карта или заявка), `relay` (сообщения через бота), `deal`
(сделка, чеки, споры), `seller` (карты и мерчант), `orders` (ордерные реквизиты, рассылка
мерчантам и в чаты, операторы), `operator` (кабинет оператора и долг), `team` (команды, `/team` в группе), `wallet`
(кошелёк: USDT в сети TON), `admin` / `admin_ops` / `admin_api` / `admin_orders` / `admin_people` (операторы,
команды, условия покупателя) / `admin_deals` (карточка и управление сделкой) / `admin_chat` (админ-панель, чат,
рассылка), `logchat` (лог-чат), `fallback` (последний). `bot/guides.py` — разделы инструкций, `bot/api/docs.py` —
страницы сайта.

`events` (история и алерты), `ton` (кошельки TON: зачисление, сбор, выплаты), `api`, `finance`.
`bot/app.py` собирает диспетчер, `bot/tasks.py` — фоновые задачи.

## Карты продавца
Карта видна покупателям, если: она включена, не заблокирована, продавец на смене и не заблокирован, по ней нет
открытой сделки, свободного баланса хватает на минимум и не исчерпан дневной лимит. Экран карты всегда пишет,
видна ли она и почему. «Включить карту» и добавление новой карты сразу выводят продавца на смену. Свои карты
продавец в «Купить USDT» не видит — там есть подсказка об этом.
Новая карта сохраняется только после экрана «Проверьте реквизиты» (шаги 1–6 → проверка → «Всё верно,
сохранить»). ФИО получателя можно указать как в банке: «Иван Иванович И.».
Продавец меняет минимум, максимум и лимит в день (сброс в 00:00 МСК), банк, ФИО получателя и номер/телефон;
реквизиты и банк нельзя менять, пока по карте идёт сделка. «Оставить в работе только эту» выключает остальные
карты, «Выключить все карты» — в «Мои карты».

## Интерфейс
- Экран с баннером правится только как подпись: если текущее сообщение текстовое (уведомление, длинный экран), бот
  удаляет его и присылает экран с баннером — первый экран после «Заявка одобрена → Открыть главное меню» уже с
  картинкой. Все экраны пользователя укладываются в лимит подписи (1024 символа, тест `test_every_screen_fits_under
  _the_banner`): «Помощь» — одно сообщение (как это работает + условия), инструкции открываются в нём же.
Каждый экран — баннер `BANNER_PATH` с подписью: по умолчанию `images/banner.mp4`, анимация Strait Pay 1280×720
без звуковой дорожки (Telegram крутит её по кругу, без звука и плеера). Исходник — `images/baner.mp4`; копию
без звука делает `ffmpeg -i images/baner.mp4 -an -c:v libx264 -crf 26 -pix_fmt yuv420p -vf scale=1280:-2
-movflags +faststart images/banner.mp4`. Можно поставить и картинку (jpg/png). Экран длиннее 1024 символов
показывается обычным сообщением. Баннер загружается один раз (даже при одновременном старте многих
пользователей) и дальше отправляется по file_id. Экраны приходят без звука уведомления — это ответ на действие
пользователя; уведомления о сделках, чеках и выводах звучат как обычно.
**Раскладка кнопок** везде одна (`emoji.kb`): сверху главное действие — одна большая кнопка; под ней короткие
кнопки по две в ряд; длинные и цветные — во всю ширину; больше двух в ряд не бывает; «Назад» (или «В меню»,
«Отмена», «Скрыть») — всегда одна и всегда последней строкой. Тесты проверяют это правило на каждой клавиатуре.
Если Telegram отклоняет custom emoji (владелец бота без Premium, неверный id), экран отправляется без них,
а изменения данных не откатываются из‑за ошибки показа.

## Главное меню и сообщения
Главное меню: большая кнопка «Кошелёк · баланс», под ней «RUB ⇄ USDT» (купить USDT за рубли) и «USDT ⇄ RUB»
(продать: панель мерчанта), затем «Ордерные реквизиты» (анкета и кабинет ордерного мерчанта; запрос реквизитов под
сумму — в «RUB ⇄ USDT»), «Оператор» (у операторов, с долгом), «Мои сделки», «Помощь», «Команда», «Strait Pay API»,
«Чат» (если подключён). Кошелёк: доступно, в сделках, в выводах, долг оператора и все комиссии по пунктам;
«Пополнить» → личный адрес USDT в сети TON, «Вывести» → любой TON-кошелёк или биржа (с memo), «История».
В разделах нет кнопок-переходов в чужие разделы (купить, пополнить, статистика продаж) — только действия раздела
и «Назад». Переключатели (приём заявок, режим ордерного мерчанта) — всегда во всю ширину (`btn(..., wide=True)`),
чтобы кнопка не прыгала при смене подписи.

## Закреп чата сообщества
Только условия: курс покупки и комиссия, курс и процент мерчанта со статичной картой, курс ордерного мерчанта.
Без статистики. Бот обновляет закреп при каждом старте и сам правит его, когда меняются курсы (проверка раз в 5 мин).

## Сообщество: обязательный чат и инфо-канал
- `join_required=1` (по умолчанию): пока пользователь не в чате сообщества и не подписан на инфо-канал (из тех,
  что заданы), вместо главного меню, покупки, продажи, кошелька и т. п. бот показывает «Последний шаг»: личная
  одноразовая ссылка в чат (на 1 ч), ссылка на канал, чат команды (по желанию) и «Проверить». Сделки в работе,
  уведомления и «Помощь» не блокируются никогда, админы проходят всегда. `0` — бот только предлагает.
- Кто где — `users.in_chat` / `in_channel`: ставятся проверкой («Проверить» спрашивает Telegram) и по вступлениям и
  выходам, которые видит бот (бот — админ чата и канала). Вышел из чата — главное меню снова за «Последним шагом».
  Смена ID чата или канала сбрасывает отметки.
- **Приветствие**: на каждое вступление в чат сообщества или чат команды бот пишет там приветствие с правилами и
  кнопками «Открыть бота» / «Инфо-канал»; предыдущее приветствие удаляется, чтобы не засорять чат.
- **Инфо-канал** (`channel_id`; «Чат и канал» → «Инфо-канал»): «Оформить канал» публикует приветствие под баннером,
  «Содержание» (закреп, ссылка на каждый пост), «Режимы работы» и пост на каждую тему: вход, покупка, продажа на
  свою карту, ордерные реквизиты, операторы, команды, кошелёк, правила. Цифры — из текущих настроек; повторное
  нажатие правит те же посты на месте. В канале обычные эмодзи (премиум-эмодзи бот туда отправить не может).

## Чат сообщества и рассылка
«Админ-панель → Чат и рассылка».
- **Чат**: задайте ID группы (`-100…`); бот — админ с правами «Приглашать» и «Закреплять». Экран показывает
  название и права бота. Кнопка «Чат» в меню выдаёт каждому **личную ссылку на один вход** (`member_limit=1`,
  1 час, имя ссылки — id пользователя, не больше 5 в час). Вступление по ссылке пишется в карточку пользователя в
  лог-чате (нужен `chat_member` в `allowed_updates` — бот включает сам); вход по чужой ссылке — алерт.
- **Закреп**: бот сам публикует и закрепляет **баннер** (`BANNER_PATH`) со сводкой в подписи — курс и пример,
  курс ордерных мерчантов, продавцы на смене и карты, ордерные мерчанты, активные сделки и заявки, оборот — и
  кнопками «Открыть бота» / «Стать ордерным мерчантом». Обновляется каждые 5 мин правкой подписи; удалили —
  опубликует и закрепит заново. «Обновить закреп» — сразу.
- **Заявки в чате**: каждая ордерная заявка публикуется в чат с кнопкой «Взять заявку в боте»; взяли или закрыли —
  сообщение меняется на «уже взята» / «закрыта», без кнопок.
- **Рассылка**: аудитория (все, продавцы с картами, на смене, ордерные мерчанты, чат) → любое сообщение (текст,
  фото, видео, файл) → предпросмотр ровно в том виде, как его увидят, → «Отправить». Идёт в фоне с лимитом
  Telegram, итог (доставлено / заблокировали бота / ошибки) приходит админу и в лог-чат. Одновременно — одна.
- **Рассылка заявок мерчантам**: ордерная заявка уходит сначала мерчантам с большим числом успешных сделок;
  досыл новым свободным мерчантам — раз в 20 с.

**Инлайн-поиск.** «Мои сделки» и «История операций» открывают поиск прямо в строке ввода (`@бот сделки …`):
фильтр по `#номеру`, сумме, статусу («спор», «завершена»), «покупка»/«продажа»; по операциям — по типу. Выбор
карточки отправляет `/deal N` или `/op N` через бота: это сообщение удаляется, а текущий экран превращается в
карточку сделки или операции. Нужно один раз включить инлайн-режим у бота: @BotFather → /setinline → бот →
подсказка, например «Поиск по сделкам…». Цвета кнопок: зелёная — купить/пополнить, красная — продать/вывести/
отменить, синяя — главное действие экрана.

**Сообщения.** Бот не удаляет свои старые сообщения — это история. Нажатие кнопки редактирует то сообщение, в
котором её нажали (оно становится текущим экраном). На команду или обычный текст приходит новый экран внизу.
Удаляется только ответ, набранный текстом на вопрос бота (сумма, номер карты, ФИО), а экран-вопрос при этом
редактируется на месте; файлы (чеки, доказательства) остаются в чате.

**Иконки.** Премиум-эмодзи — только в заголовке экрана и в строке результата (✅ / ⚠️); в фактах, шагах и
подзаголовках их нет (`ui.clean`). На кнопках иконка только у выделенных цветом главных действий.

## Команды
Команды: `/start` (`/menu`), `/buy`, `/sell`, `/wallet`, `/deals`, `/help`, `/support`, для админов `/admin`,
`/deal N`, `/user ID|@ник`, `/find запрос`, `/teams`, `/admins`, `/addadmin`, `/deladmin`, `/signups`; в группах —
`/help` (инструкции), `/team` (тимлид подключает чат). В админ-чате те же команды админов работают прямо в теме
(`/help` — справка, `/team ID` — карточка команды, `/setts` — настройка тем), неизвестная команда — справка;
меню команд ставится при запуске. Команда остаётся в чате, бот отвечает новым экраном внизу, у прошлого
экрана убираются кнопки. Любая команда завершает текущий шаг ввода: `/cancel` или опечатка никогда не
станет суммой, текстом обращения или доказательством — бот ответит «Неизвестная команда».
Ответ на любое сообщение появляется под ним, прошлый экран удаляется (кнопки кликов по-прежнему
редактируют экран на месте). Удаляются только ответы на вопросы бота (сумма, номер карты, ФИО, чек) и только
если они обработаны; обычный текст и команды не удаляются.
Обновления одного пользователя обрабатываются строго по очереди (`bot/storage.py: UserIsolation`): команда и
сообщение, отправленные одновременно, не гоняются за экран и состояние. Если обработчик упал, пользователь
всё равно получает ответ (алерт на кнопке или сообщение с «В меню»), шаг ввода сбрасывается.
Сообщения в группах игнорируются, кроме админ-чата: там команды админов и их ответы на вопросы бота
обрабатываются на месте, обычная переписка админов — нет.

## Истечение сделки и поздний чек
После истечения срока оплаты залог продавца ещё `late_hold_minutes` (30) остаётся замороженным: если
покупатель платил в последние минуты и пришлёт чек, сделка вернётся продавцу на проверку, а продавец не
сможет за это время вывести эти USDT. Потом залог освобождается автоматически. Чек после этого (до
`late_minutes`) примется, только если у продавца снова есть средства, иначе уходит админам.

## Чеки
По умолчанию только PDF; бот проверяет сигнатуру `%PDF`, переименованные файлы не принимаются.
`receipt_images=1` разрешает фото и скриншоты (их проще подделать — продавец всё равно сверяет поступление).

## Админ-чат: темы, закрепы и живые карточки
**Новая структура тем при старте.** `logchat.LAYOUT` — версия набора тем. Если для админ-чата сохранена другая
версия, при запуске бот забывает старые темы (их удаляете вы), карточки и сообщение статистики, создаёт все темы
заново и закрепляет в каждой справку. Каждый старт также обновляет закрепы, если их текст изменился. Повторный
старт ничего не дублирует.

Включите в группе **Темы** (Настройки группы → Темы), добавьте бота админом с правами «Управление темами»,
«Удаление сообщений», «Закрепление» и «Приглашать пользователей» и напишите в группе **`/setts`** — только от
администратора бота. Бот запомнит группу как админ-чат (`LOG_CHAT_ID` менять не нужно), создаст темы и в каждой
закрепит справку: что приходит само, что делают кнопки, а в «🎛 Управление» и «⚠️ Требует внимания» — список
команд. Повторный `/setts` ничего не дублирует: закреп правится, только если текст изменился (отчёт: тем,
закрепов новых / обновлено / без изменений). Id тем хранятся в БД; удалённую тему бот создаст заново.
Темы: ⚠️ Требует внимания, 🎛 Управление, 📝 Заявки на вход, 📊 Статистика, 💱 Сделки, 🧾 Ордерные реквизиты,
🟣 Bybit-ордера, 🧑‍💻 Операторы и долги, 🫂 Команды и тимлиды, 📥 Пополнения, 📤 Выводы, 🔑 API, 🤝 Ордерные мерчанты,
👤 Пользователи, 💳 Карты, ✏️ Корректировки, 💬 Обращения, 👥 Чат и рассылки, 🛡 Действия админов, 🛑 Ошибки бота,
⚙️ Сервис.

У каждой операции — **одна карточка** в своей теме, в карточном стиле: заголовок со статусом (🟡 в процессе,
🟢 успешно, 🟠 нужно внимание, 🔴 отказ, ⚪️ отменено) и номером-ссылкой, затем поля «подпись → значение на
ветке» (люди — ссылками на их карточки в боте, суммы, курс, доход площадки, реквизиты, сеть), свёрнутая
«История» последних событий и время (МСК). Заявки (команда, ордерный мерчант, API, корректировка на второго
админа) решаются **прямо на карточке** — «Одобрить / Отклонить»; решение хранится в данных, поэтому любая
копия карточки показывает, кто и когда решил («✅ Одобрено · имя»). «Подробнее» открывает полный экран на месте.
При смене статуса карточка **редактируется** тихо, а всё, что требует админа, дублируется в «Требует внимания»
со звуком. Без тем всё идёт в общий чат: рядовые шаги правят карточку, проблема публикует свежую карточку внизу.

**🛡 Действия админов** — каждое действие отдельным постом: кто (ссылка), что сделал (бан, баланс, настройка,
решение спора, назначение админа…), с кем или с чем, детали, время. Тот же журнал — «Админ-панель → Журнал».

**🛑 Ошибки бота** — каждая ошибка бота: что (`KeyError: …`), где (`файл:строка · функция`), когда и свёрнутый
хвост трейсбека. Одна и та же ошибка за 30 минут — один пост со счётчиком «Повторов: ×N» (правится на 2, 3, 5,
10, 25…); не больше 25 новых постов в минуту. Только в группу — в личку трейсбеки не уходят.

## Лог-чат: что попадает
`log_all=1` (по умолчанию) — в лог-чат идут все шаги: новый пользователь, открытие сделки, чек, завершение,
отмена, истечение, решение спора, пополнения, выводы, новые карты. Проблемы помечены «нужно внимание»:
отклонённый сетью перевод, нехватка USDT или газа на горячем кошельке, вывод `unknown`, споры, поздний чек без
средств, недоставленные уведомления, спор без решения дольше 2 ч. `log_all=0` — только проблемы.
`LOG_THREAD_ID` — топик, если лог-чат форум. Перед выплатой бот сверяет баланс горячего кошелька: если его
не хватает, пользователь ничего не теряет, вывод ждёт в очереди, админам приходит алерт.
Свой баланс администратор изменить не может: корректировку себе проводит другой администратор.

## Emoji
`EMOJI_MODE=premium` — custom emoji из каталога Zulut30 (`bot/emoji.py`). Telegram показывает их, только если
у владельца бота есть Telegram Premium (или у бота купленный на Fragment юзернейм); иначе клиенты видят
обычные fallback-эмодзи — отключить fallback в Telegram нельзя, он обязателен для тега `<tg-emoji>`.
`EMOJI_MODE=plain` — только обычные эмодзи; `EMOJI_MODE=none` — интерфейс полностью без эмодзи и иконок кнопок.
