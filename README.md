# Strait Pay — P2P-обмен USDT ⇄ RUB в Telegram

aiogram 3 · PostgreSQL · xRocket Pay API (новый, не Legacy).

## Запуск
```bash
cp .env.example .env            # заполнить BOT_TOKEN, ADMIN_IDS, XROCKET_TOKEN (TON_* больше не нужны)
docker compose up -d db         # или свой PostgreSQL в DATABASE_URL
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m bot
```
Схема БД: ограничения `balance >= 0` и `frozen >= 0` на уровне PostgreSQL, составные индексы под частые
запросы (сделки покупателя и продавца по статусу, журнал пользователя, алерты); тест `test_migrated_schema_equals_fresh_schema`
сверяет колонки, индексы и CHECK-ограничения свежей и мигрированной базы.
При старте бот применяет версионные миграции PostgreSQL (`bot/models.py: MIGRATIONS`, таблица
`schema_version`), затем создаёт недостающие новые таблицы. Существующая БД обновляется явными `ALTER`.
На одну БД допускается **один процесс** бота (pg advisory lock): второй экземпляр завершится с ошибкой.
Состояние диалога хранится в БД (`fsm_state`) и переживает рестарт; в процессе держится его копия, поэтому
чтение состояния не ходит в БД. PDF, присланный во время неоплаченной сделки без активного шага, всё равно
примется как чек. Пул PostgreSQL: 10+20 соединений, `lock_timeout` 15 с — ожидание блокировки не вешает бота.

## Тесты
```bash
.venv/bin/python -m pytest -q                       # SQLite
# полный набор, включая гонки SELECT FOR UPDATE и миграцию старой схемы, на одноразовой PostgreSQL:
P2P_TEST_PG=postgresql+asyncpg://p2p@127.0.0.1:5432/p2p_test .venv/bin/python -m pytest -q
```
Тестовая БД из `P2P_TEST_PG` **полностью очищается** (DROP SCHEMA public) — не указывайте рабочую.

## xRocket — все деньги идут через него
Своего подключения к блокчейну у бота нет: пополнения и выводы — только через xRocket Pay API.
- Токен: @xRocket → Rocket Pay → приложение → API token. Версия API приложения — **Pay API** (не Legacy).
- Для тестов: @xrocket_testnet_bot и его base URL в `XROCKET_BASE_URL`.
- **Сети** берутся из `GET /api/v1/currencies` (сети USDT, кэш 1 ч): TON, TRC-20, ERC-20, BEP-20, Solana — какие
  доступны в xRocket, те и показывает бот.
- **Пополнение счётом**: `POST /api/v1/invoices` на сумму, оплата в @xRocket.
- **Пополнение по адресу**: пользователь выбирает сеть → бот создаёт счёт без фиксированной суммы (один платёж от
  `deposit_min`, живёт 24 ч) и берёт адрес у xRocket: `POST /api/v1/invoices/payments/address` (`payNetwork`). Бот
  показывает именно этот адрес; повторное нажатие той же сети показывает тот же адрес, пока он действует.
- Статус счёта опрашивается раз в 60 с (`GET /api/v1/invoice`), по завершении бот сверяет
  `GET /api/v1/invoice/payments` и зачисляет **фактически полученное минус `deposit_fee`** (1,5% по умолчанию —
  и счётом, и по адресу); комиссия идёт в доход площадки. Счёт с платежом `pending` не закрывается.
- **Комиссия вывода**: `withdraw_pct` (1,5%) от суммы списания — и чеком, и на кошелёк; плюс фикс: чеком
  `withdraw_fee` (0), на кошелёк `chain_withdraw_fee` (3 USDT, комиссия сети xRocket внутри; если сеть берёт больше —
  берётся комиссия сети). 100 USDT чеком → чек 98,5; 10 USDT в TRC-20 → придёт 6,85 (0,15 + 3).
- **Вывод чеком**: `POST /api/v1/cheques` с `targetType=telegram_user_id` — активирует только сам пользователь.
  Нет ответа (сеть/5xx/429) → статус `unknown`, деньги удержаны, сверка по `clientChequeId` раз в 5 мин; если чек не
  найден, админ возвращает сумму кнопкой (повтор создания с тем же id и отмена — двойной выплаты не будет).
- **Вывод на кошелёк**: сеть → адрес (проверка формата сети; адреса пополнения бота не принимаются; кнопка «Как в
  прошлый раз») → memo (только TON) → сумма → подтверждение. `POST /api/v1/withdrawals` (`network`, `asset=USDT`,
  `clientWithdrawalId=wd-<id>`). Комиссия = `chain_withdraw_fee` (площадке) + комиссия сети из
  `GET /api/v1/withdrawal-quotas` (платится xRocket из фикс. части). Статус сверяется раз в минуту
  (`GET /api/v1/withdrawal`): `COMPLETED` → выполнен с хешем, `FAIL`/отказ → возврат, xRocket не знает id →
  повтор с тем же `clientWithdrawalId`.
- **Переход со старой версии**: собственные TON-кошельки (`TON_SEED`) удалены. Перед обновлением убедитесь, что на
  старых адресах пополнения нет USDT (раньше их переводил автоперевод). Таблицы `ton_*` остаются в БД как история.

## Вход по заявке
`signup_review = 1` (по умолчанию; «Настройки → Правила и лог-чат»): новый пользователь не видит бота, пока его не
впустят. Анкета: **кто вы** (P2P-продавец / покупатель) → **оборот в день** (кнопкой или своей суммой) → продавец
прикладывает **скриншот баланса или оборота** → «Проверьте заявку» → «Отправить заявку». Заявка (со скриншотом)
публикуется в лог-чате в ветке **«📝 Заявки на вход»** с кнопками «Одобрить» / «Отклонить» прямо под ней (нет лог-чата —
админам в личку); она же — в «Админ-панель → Заявки на вход» (там ещё «Отклонить с причиной» и «Показать скриншот»).
Одобрили — пользователю приходит приветствие с кнопкой **«Открыть главное меню»**; отклонили — причина, новая
заявка через 24 ч. Карточка в ветке после решения меняется: кто решил и когда, кнопки убираются. Ссылка тимлида
работает сразу — пользователь попадает в команду ещё до решения. Пока не впустили, любое сообщение и любая кнопка
возвращают к анкете (`handlers/signup.py`, фильтр на роутере). Все, кто был в боте до обновления, впущены
(миграция 15: `users.access`, таблица `signups`). `signup_review = 0` — бот открыт всем, никто не ждёт.

## Сообщения через бота
Кнопка «Написать» на экране сделки: покупатель, мерчант и оператор пишут друг другу и администрации; администратор —
кому угодно (из карточки сделки или профиля). Сообщение приходит с кнопкой **«Ответить»**, переписка идёт в боте и
попадает в историю сделки (её видно в лог-чате). **Ссылки и @юзернеймы запрещены** (кроме администрации): такое
сообщение не отправляется, админам уходит алерт. Не больше 30 сообщений в час от пользователя.

## Strait Pay API для сервисов
Полная документация: [docs/API.md](docs/API.md), она же отдаётся по `GET /docs`. Канон бренда: [docs/BRAND.md](docs/BRAND.md).
- Доступ по заявке: бот → «Strait Pay API» (`/api`) → анкета (проект, ссылка, трафик, оборот) → админ одобряет или
  отклоняет с причиной в «Админ-панель → API для сервисов» → пользователь выпускает токен (показывается один раз,
  в БД только SHA-256), задаёт вебхук и берёт секрет подписи.
- Заказ по API — обычная сделка, где покупатель — владелец токена (`deals.api_client_id`). У заказов свои лимиты
  (сумма, сутки, число неоплаченных, запросов в секунду) вместо ограничений для частного покупателя. USDT по
  успешному заказу идут на баланс владельца на обычных условиях. Личное меню, «Мои сделки» и уведомления
  владельца API-заказами не засоряются: о смене статуса сообщают вебхуки (outbox `api_events`, подпись
  HMAC-SHA256, повторы до суток, только публичные https-адреса).
- Чек по API проверяется по содержимому (PDF), копия уходит владельцу токена в чат — так Telegram выдаёт file_id,
  дальше чек идёт продавцу тем же путём, что и из бота.
- Запуск: `API_ENABLED=true`, `API_HOST`/`API_PORT` (по умолчанию 127.0.0.1:8080), наружу — через HTTPS-прокси на
  вашем домене, `API_PUBLIC_URL=https://api.<домен>`.

## Очередь выводов и финансы
- **Выводы ждут, а не отклоняются.** Если на балансе приложения xRocket не хватает USDT (для вывода на кошелёк —
  вместе с комиссией сети), вывод принимается и списывается, пользователь видит «в обработке», а фоновая задача раз в
  30 с отправляет очередь **строго по порядку**, как только баланс позволяет (маленький вывод не обгоняет большой).
  Если xRocket ответил «не хватает средств» уже при отправке — вывод возвращается в очередь, а не отменяется. Пока
  вывод в очереди, пользователь может его отменить в кошельке (деньги возвращаются). Админам — алерт раз в час:
  сколько ждёт и сколько пополнить.
- **Финансы** («Админ-панель → Финансы» и живое сообщение в ветке «📊 Статистика и финансы», обновляется раз в 10
  мин): что есть (баланс xRocket), что должны пользователям (балансы, заморозка в сделках, выводы в пути), **сколько можно забрать** = есть − должны
  (прибыль уже внутри), прибыль за 24 ч / 7 / 30 дней / всё время, оборот, очередь выводов с подсказкой, на сколько
  пополнить xRocket.

## Деньги
`usdt = rub / курс`; с продавца замораживается `usdt·(1−%продавца)`, покупатель получает `usdt·(1−%площадки)`,
разница — доход площадки. Пример 10 000 ₽ / 100 / 5% / 6% → 95 / 94 / 1. Всё меняется в админке.

Процент мерчанта со **статичной картой** — `seller_pct` (по умолчанию 5%, бывает личный), не больше процента
площадки. **Ордерные мерчанты работают без процента, по фиксированному курсу** `order_rate` (по умолчанию 104 ₽):
мерчант отдаёт `сумма / order_rate` USDT, покупатель получает как обычно, разница — площадке. 10 400 ₽ по ордеру →
мерчант отдаёт 100 USDT, покупатель получает 97,76, площадке 2,24. `order_rate` не может быть выше
`rate / (1 − platform_pct)` — иначе площадка доплачивала бы покупателю; бот не даст сохранить такой курс, в том числе
при снижении `rate` (сначала снизьте курс ордерного). Условия фиксируются в сделке при её создании.

**Личные условия покупателя.** Профиль пользователя → «Условия покупателя»: свой курс и/или процент (как у
API-клиента). Действуют на все его покупки — по картам и ордерным реквизитам; сторона мерчанта не меняется, разница —
площадке; сделка, где площадка ушла бы в минус, не создаётся. Покупатель видит «ваши условия» на экранах покупки.

**Тимлиды.** С каждой завершённой сделки, где мерчант — участник команды (не сам тимлид), тимлид получает
`team_pct` (1%) от суммы сделки в USDT по её курсу (10 400 ₽ / 100 → 1,04 USDT) на баланс. Платит площадка из своего
дохода по сделке и не больше него; в сделке это `team_id` / `team_fee`, в журнале — `team_fee`.

**API-клиенты — свои условия.** У подключения по API можно задать курс и процент («Админ-панель → API-клиенты →
клиент → Курс клиента / Процент клиента», «-» — общие). Они одинаковы для всех его заказов — и по статичным картам,
и по ордерным реквизитам: курс 100 и 7% → с 10 000 ₽ клиент получает 93 USDT. Сторона мерчанта не меняется
(процент карты / курс ордерного), разница — площадке; экран клиента показывает маржу для карты и для ордера, а
заказ, где площадка ушла бы в минус, не создаётся. `GET /v1/rates` отдаёт клиенту его условия.

**Управление — «Админ-панель → Комиссии и проценты»**: все ставки на одном экране (что платит покупатель,
процент мерчанта по карте, фиксированный курс ордерного мерчанта и его потолок, маржа площадки, комиссии пополнения
и выводов — процент и фикс, процент тимлида, списки личных ставок мерчантов и условий покупателей, пример на 10 000 ₽), каждая меняется кнопкой, после сохранения экран возвращается сюда же. **Личный
процент** (только статичная карта): профиль пользователя → «Процент мерчанта», «Сбросить на общую». Действует для
новых сделок; выше ставки покупателя не применяется, даже если процент площадки потом снизят. Изменение приходит
мерчанту уведомлением, уходит в лог-чат и журнал действий. Личных ставок для ордеров нет (миграция 12 удаляет
`users.pct_order`).

## Сделки: сроки и споры
- `deal_minutes` — время на перевод и PDF-чек. Чек, загруженный после срока (в пределах `late_minutes`),
  снова замораживает средства продавца и возвращает сделку ему на проверку; если у продавца уже нет средств,
  чек уходит администрации.
- Через `confirm_minutes` после чека продавцу приходит напоминание, а покупатель может открыть спор.
  Через `escalate_minutes` спор открывается автоматически.
- В споре обе стороны добавляют доказательства (видео, фото, PDF, текст). Решение админа — только после
  экрана подтверждения с суммами для каждой стороны.
- Экран сделки показывает этап (1 — перевод и чек, 2 — проверка поступления, 3 — зачисление) и кнопки
  «Скопировать номер/телефон» и «Скопировать сумму». Перед отменой покупатель видит, сколько отмен у него осталось.
- Решение по спору админ может сопроводить комментарием (5–500 символов): он хранится в `deals.resolution`,
  приходит обеим сторонам и виден на экране сделки. Списки споров показывают, сколько прошло с момента чека.
- `buyer_fail_limit` — сколько отменённых/просроченных покупок за сутки допускается до блокировки покупок.
  Отмены из-за бана участника или админом (статус `void`) не считаются.

## Администрирование
- **Панель** («Админ-панель», `/admin`): блок «Требует внимания» по пунктам (споры, выводы на проверке, ордера без
  оператора, обращения, анкеты мерчантов, заявки на команды и API…) с кнопкой на каждую очередь; сводка (пользователи,
  оборот, доход, балансы и xRocket, долг операторов); разделы парами: Найти · Сделки, Ввод и вывод · Карты,
  Ордерные мерчанты · Операторы, Команды · API-клиенты, Комиссии · Настройки, Чат и рассылка · Обращения,
  Отчёты CSV · Журнал. История любой операции показывает последние события (длинная — обрезается сверху).
- **Сделка по номеру**: `/deal 15`, «Найти» → `#15` или «Открыть» на карточке в лог-чате (в заголовке карточки —
  `/deal N`). Карточка: кто создал (покупатель), кто принял (мерчант), оператор — с @username и числом сделок;
  деньги, реквизиты, сроки, чек и спор, последние события. **Управление**: «Выдать реквизиты самому» (для заявки:
  админ становится её оператором, мерчант снимается и его заморозка возвращается; рубли — на реквизиты админа, долга
  нет), «Изменить сумму» (пересчёт по условиям сделки, заморозка мерчанта следует за суммой), «Продлить +15 мин»,
  «Закрыть заявку» / «Отменить сделку», «Завершить: USDT покупателю», «Отменить: в пользу продавца», написать
  любому участнику.
- **Профиль**: роли (оператор, ордерный мерчант, тимлид, участник команды), долг оператора, личные условия; кнопки
  «Процент мерчанта», «Условия покупателя», «Оператор: долг и ордера».
- **Профиль по Telegram ID.** «Найти»: ID, `@username`, `#15` (сделка), `в482` (вывод), `п12` (пополнение),
  номер карты/телефона. Поиск по выводу/пополнению открывает профиль владельца с кнопкой на операцию.
  В профиле — доступно/заморожено, покупки и продажи отдельно (объём, отмены по причинам), споры,
  пополнено/выведено; кнопки «Сделки», «Операции», «Карты», «Споры», «Выводы и пополнения», «Изменить баланс».
- **Корректировка баланса**: начислить/списать → сумма → причина из списка («Другое» — с комментарием) →
  черновик `Корректировка #N` в БД с балансом «до → после» → «Подтвердить». Повторное нажатие и рестарт бота
  ничего не меняют. Списывается только доступный баланс; замороженное меняется только через сделки.
  Ledger получает запись `adj:N` с причиной; действие пишется в журнал и уходит алертом.
  `adjust_approval_usdt` > 0 — от этой суммы нужен второй администратор (по умолчанию выключено).
- **Карточки операций**: вывод (списано, чек, комиссия, `clientChequeId`, ответ xRocket, следующее действие,
  «Проверить в xRocket», «История вывода»), пополнение, сделка/спор, корректировка, обращение. Возврат по
  выводу `unknown` доступен только после ответа xRocket «чек не найден».
- **Журнал событий и алерты (outbox).** Событие сохраняется в таблицу `events` в той же транзакции, что и
  изменение; отправку в лог-чат выполняет фоновая задача и повторяет её при сбое Telegram (до часа; недоставленные
  видны на панели). В чат уходит короткое сообщение «что · №» с кнопкой «Открыть» — реквизиты и файлы только
  на карточке. Алерты: вывод `unknown`, отменённый чек/возврат, частичная оплата истёкшего счёта, новый спор и
  автоэскалация, недоставленные уведомления продавцу, корректировки, бан пользователя/карты, ошибки сверки
  (не чаще раза в час на операцию), обращения. Штатные операции — только в истории и сводке.
- **Обращения** пользователей со статусами «ждёт ответа / отвечено / закрыто»; ответ из карточки.
- **Настройки** разбиты на разделы (курс и комиссии, сроки, кошелёк, правила, тексты); значения показаны
  с единицами, у параметра видно значение по умолчанию и формат ввода, после сохранения — «было → стало».
  Баланс xRocket на панели кэшируется на 60 с (перед выводом всегда запрашивается заново).
- **Отчёты CSV** за 1/7/30 дней: сделки, журнал операций (`delta` и `frozen_delta`), пополнения и выводы.
- **Ledger**: `delta` — изменение доступно+заморожено, `frozen_delta` — изменение заморозки; заморозка и
  разморозка по сделкам журналируются. «Операции» в профиле сверяют журнал с балансом.
- Лог-чат может быть группой, но экраны открываются в личном чате администратора с ботом: без него бот
  покажет подсказку «Откройте личный чат с ботом».

## Ордерные реквизиты (реквизиты под сумму)
Покупатель нажимает «RUB ⇄ USDT» и просто отправляет сумму в рублях — без списков и фильтров. Бот сам выбирает
самую надёжную статичную карту под сумму (больше завершённых сделок), а если её нет — предлагает **заявку на
реквизиты под точную сумму** (`order_min_rub`–`order_max_rub`): «Создать заявку» → статус `searching`. Дальше:

1. **Рассылка.** Заявка уходит **каждому** одобренному ордерному мерчанту — без лимитов сумм и без «включить
   приём»: мерчант сам решает, брать или нет. В сообщении по пунктам: сумма перевода, банк покупателя, курс ордера,
   сумма ордера в USDT, сколько это по курсу сервиса и доход мерчанта, срок. Кнопки: «Взять · Bybit-ордер» (баланс не
   нужен) и «Взять · с баланса» (только если свободного USDT хватает). Та же заявка публикуется в чат сообщества и
   в чаты всех команд с кнопкой «Взять заявку в боте» (`t.me/<бот>?start=o<id>`, в чате команды
   `o<id>_t<команда>`): бот открывает заявку и те же две кнопки, не-мерчанту предлагает анкету. Раз в 20 с заявка
   досылается новым мерчантам и чатам; не доставленное (бот заблокирован) не повторяется. Некому отправить — алерт.
2. **Взятие** — кто первым нажал, тот и взял (блокировка строки сделки). «С баланса»: `seller_debit` мерчанта
   **замораживается**; «Bybit-ордер»: ничего не замораживается, дальше ссылка и оператор (см. ниже). Сделка →
   `assigned`, у остальных мерчантов и в чатах сообщение меняется на «уже взята».
3. **Реквизиты** (режим «Баланс»). Мерчант за `order_take_minutes` (10 мин) выдаёт реквизиты: одним нажатием «как в прошлый раз»
   (последние 3 набора) или новые — карта/СБП → банк → номер → ФИО. Время на оплату выбирается кнопкой: от
   `order_pay_minutes` (15) до 60 мин. Реквизиты разовые: в общий список «Купить USDT» не попадают. Сделка → `waiting_payment`.
4. Дальше обычная сделка: покупатель переводит и присылает PDF → мерчант проверяет поступление → «Деньги пришли»
   (USDT покупателю, доход мерчанту) или спор. Работают автоспор, поздний чек, удержание залога и все решения админа.
5. **Таймауты.** Мерчант отказался или не выдал реквизиты вовремя → заморозка снимается, заявка возвращается в
   поиск, повторно этому мерчанту не приходит. Никто не взял за `order_search_minutes` (15) → заявка закрывается с
   причиной `no_merchant`, в лимит отмен покупателя это не засчитывается. Покупатель может отменить заявку до выдачи
   реквизитов (у мерчанта снимается заморозка).

**Ордерные мерчанты.** «Ордерные реквизиты → Заполнить анкету» (4 шага): откуда берёт реквизиты и ордера, как
быстро выдаёт, какие банки, о себе. Анкета уходит алертом в лог-чат и сообщением каждому админу. В «Админ-панель →
Ордерные мерчанты» её одобряют или отклоняют с причиной (подать снова — через 24 ч), там же приостанавливают и
возобновляют. Кабинет: «На линии: заявки приходят все», курс, свободный баланс и на какую заявку его хватит «с
баланса», заявки в работе, свободные заявки (открыть и взять), результаты, время на оплату по умолчанию. Лимитов,
тумблера приёма и режима больше нет (миграция 14 удаляет `min_rub`, `max_rub`, `max_open_rub`, `accepting`, `mode`).

**API.** `POST /v1/orders` без подходящей карты открывает ордерную заявку: ответ `202`, статус
`searching_requisites` → `merchant_assigned` → [`requisites_check`] → реквизиты придут вебхуком со статусом
`awaiting_payment`. В заказе есть `next_action` и `stage`, история статусов — `GET /v1/orders/{id}/history`,
ордерные мерчанты на смене — `order_requisites` в `GET /v1/liquidity`. Отключить: `"order_requisites": false`.

### Bybit-ордера и операторы
Нет статичной карты под сумму → заявка (из бота или `POST /v1/orders`, ответ 202) уходит всем ордерным мерчантам
и в чаты; первый нажавший «Взять» её получает и выбирает, как работать:
- **Bybit-ордер** — баланс в боте не нужен, ничего не замораживается. Мерчант присылает ссылку на ордер Bybit P2P
  (`https://…bybit.com/…`, одна ссылка — одна заявка) → статус `checking` → **каждому оператору** приходит сообщение
  по пунктам (сумма ордера, курс мерчанта, на сколько USDT зайти, банк покупателя, мерчант, срок) **без ссылки** и с
  кнопкой «Принять ордер». Первый принявший получает ссылку и экран выдачи реквизитов, у остальных сообщение
  меняется на «принял другой оператор». Оператор может «Вернуть другим» (ордер снова уходит всем операторам) или
  «Отклонить ссылку» (заявка возвращается мерчанту). Реквизиты из ордера уходят покупателю (в бот или вебхуком по
  API). Чек: оператору — с кнопками «Подтвердить» / «Спор», мерчанту — только PDF. Подтверждение зачисляет
  покупателю USDT **с баланса площадки**, а USDT ордера пришли оператору на Bybit — **это его долг** (см. ниже).
  Спор оператора: причина → видео из ЛК или выписка → решается сразу в его пользу (нет оплаты — отмена, другая
  сумма — проведение по факту). Ордер не принят / реквизиты не выданы за `order_check_minutes` (15 мин) — заявка
  закрывается (`no_merchant`), админам — алерт.
- **С баланса** — под заявку замораживаются `сумма / order_rate` USDT мерчанта, реквизиты выдаёт и оплату
  подтверждает он сам.

### Операторы и их долг
- **Кто оператор**: «Админ-панель → Операторы → Добавить оператора» (ID или @username; человек должен запустить
  бота), там же «Убрать из операторов». `OPERATOR_IDS` из `.env` тоже работают. Пока нет ни одного — операторы админы.
- **Долг**: каждое подтверждённое оператором Bybit-ордером (или решённое в пользу покупателя) добавляет к его долгу
  `seller_debit` — USDT ордера на его Bybit. Таблица `operators.debt`, история — события `op:<id>`.
- **Кабинет «Оператор»** (кнопка в меню): долг, ордера в работе, свободные ордера («Принять ордер»), результаты,
  «Погасить через xRocket» — счёт на всю сумму долга (`deposits.purpose = debt`, без комиссии; оплачен — долг
  уменьшается, переплата идёт на баланс) и «Погасить с баланса». Админ может «Списать долг вручную».
- В «Финансах» и на панели — «Долг операторов»; в «можно забрать» он не входит, пока не погашен.

### Команды и тимлиды
- «Команда» в меню → «Создать команду»: название и о себе → админ одобряет или отклоняет с причиной в
  «Админ-панель → Команды» (подать снова — через 24 ч), там же приостановка и личный процент тимлида.
- Одобренный тимлид получает реферальную ссылку `t.me/<бот>?start=t<id>`: кто запустит бота по ней (и ещё не в
  команде) — участник его команды и получает кнопку «Вступить в чат команды» (личная ссылка на один вход).
- Чат команды: тимлид добавляет бота админом группы (приглашать, закреплять) и пишет в ней `/team`. В чат приходят
  все ордерные заявки со ссылкой `?start=o<id>_t<команда>` — по ней можно и взять заявку, и попасть в команду.
- Тимлиду — `team_pct` (1%) от каждой сделки участника (см. «Деньги»). Кабинет тимлида: ссылка, участники, чат,
  доход сегодня / 7 дней / всего.
Статусы сделки: `searching` → `assigned` → [`checking`] → `waiting_payment` → `paid` → `completed` / `dispute`.


## Для продавцов (мерчантов)
- **Панель мерчанта** («Продать USDT»): статус смены, сегодняшний доход, карты с видимостью, «В работе (N)» —
  все открытые сделки (обычные и ордерные), где нужно действие — сверху; «Статистика», «Ордерные реквизиты»,
  «Настройки», «Пополнить».
- **Статистика и доход**: сегодня / 7 / 30 дней / всё время — сделки (ордерных отдельно), оборот, средний чек,
  доход, доля успешных, среднее время подтверждения, споры; доход по дням за неделю.
- **Настройки мерчанта**: уведомления о сделках и чеках со звуком или без (удобно ночью), выключить все карты.
- **Ордерный кабинет**: результаты по ордерам (сегодня, 7 дней, всего, успешность), лимиты, время на оплату по
  умолчанию; сохранённые реквизиты выдаются в два нажатия (шаблон → «Выдать»).
- В «Мои карты» — строка «Сегодня: N сделок на X ₽ · доход +Y USDT»; «Статистика продаж» — сегодня / 7 / 30 дней:
  сделки, оборот, доход, среднее время подтверждения, споры.
- За 5 мин до автозавершения смены приходит напоминание с кнопкой «Остаюсь на смене».
- **Повторный чек**: один и тот же файл (Telegram `file_unique_id`) в двух сделках — продавец видит
  предупреждение в уведомлении о чеке, админам уходит алерт. Чек, пришедший в ту же секунду, когда сделка
  истекла, не теряется — обрабатывается как поздний.
- Админу чек и доказательства спора приходят альбомами (фото/видео и документы по 10), пояснения сторон — одним
  сообщением.

## Карты продавца
Карта видна покупателям, если: она включена, не заблокирована, продавец на смене и не заблокирован, по ней нет
открытой сделки, свободного баланса хватает на минимум и не исчерпан дневной лимит. Экран карты всегда пишет,
видна ли она и почему. «Включить карту» и добавление новой карты сразу выводят продавца на смену. Свои карты
продавец в «Купить USDT» не видит — там есть подсказка об этом.
Новая карта сохраняется только после экрана «Проверьте реквизиты» (шаги 1–6 → проверка → «Всё верно,
сохранить»). ФИО получателя можно указать как в банке: «Иван Иванович И.».
Продавец меняет минимум, максимум и лимит в день (сброс в 00:00 МСК), банк, ФИО получателя и номер/телефон;
реквизиты и банк нельзя менять, пока по карте идёт сделка. «Оставить в работе только эту» выключает остальные
карты, «Выключить все карты» — в «Мои карты».

## Интерфейс
Каждый экран — баннер `BANNER_PATH` с подписью: по умолчанию `images/banner.mp4`, анимация Strait Pay 1280×720
без звуковой дорожки (Telegram крутит её по кругу, без звука и плеера). Исходник — `images/baner.mp4`; копию
без звука делает `ffmpeg -i images/baner.mp4 -an -c:v libx264 -crf 26 -pix_fmt yuv420p -vf scale=1280:-2
-movflags +faststart images/banner.mp4`. Можно поставить и картинку (jpg/png). Экран длиннее 1024 символов
показывается обычным сообщением. Баннер загружается один раз (даже при одновременном старте многих
пользователей) и дальше отправляется по file_id. Экраны приходят без звука уведомления — это ответ на действие
пользователя; уведомления о сделках, чеках и выводах звучат как обычно.
**Раскладка кнопок** везде одна (`emoji.kb`): сверху главное действие — одна большая кнопка; под ней короткие
кнопки по две в ряд; длинные и цветные — во всю ширину; больше двух в ряд не бывает; «Назад» (или «В меню»,
«Отмена», «Скрыть») — всегда одна и всегда последней строкой. Тесты проверяют это правило на каждой клавиатуре.
Если Telegram отклоняет custom emoji (владелец бота без Premium, неверный id), экран отправляется без них,
а изменения данных не откатываются из‑за ошибки показа.

## Главное меню и сообщения
Главное меню: большая кнопка «Кошелёк · баланс», под ней «RUB ⇄ USDT» (купить USDT за рубли) и «USDT ⇄ RUB»
(продать: панель мерчанта), затем «Ордерные реквизиты» (анкета и кабинет ордерного мерчанта; запрос реквизитов под
сумму — в «RUB ⇄ USDT»), «Оператор» (у операторов, с долгом), «Мои сделки», «Помощь», «Команда», «Strait Pay API»,
«Чат» (если подключён). Кошелёк: доступно, в сделках, в выводах, долг оператора и все комиссии по пунктам;
«Пополнить» → счёт xRocket или адрес в сети, «Вывести» → чек xRocket или кошелёк в сети, «История».
В разделах нет кнопок-переходов в чужие разделы (купить, пополнить, статистика продаж) — только действия раздела
и «Назад». Переключатели (приём заявок, режим ордерного мерчанта) — всегда во всю ширину (`btn(..., wide=True)`),
чтобы кнопка не прыгала при смене подписи.

## Чат сообщества и рассылка
«Админ-панель → Чат и рассылка».
- **Чат**: задайте ID группы (`-100…`); бот — админ с правами «Приглашать» и «Закреплять». Экран показывает
  название и права бота. Кнопка «Чат» в меню выдаёт каждому **личную ссылку на один вход** (`member_limit=1`,
  1 час, имя ссылки — id пользователя, не больше 5 в час). Вступление по ссылке пишется в карточку пользователя в
  лог-чате (нужен `chat_member` в `allowed_updates` — бот включает сам); вход по чужой ссылке — алерт.
- **Закреп**: бот сам публикует и закрепляет **баннер** (`BANNER_PATH`) со сводкой в подписи — курс и пример,
  курс ордерных мерчантов, продавцы на смене и карты, ордерные мерчанты, активные сделки и заявки, оборот — и
  кнопками «Открыть бота» / «Стать ордерным мерчантом». Обновляется каждые 5 мин правкой подписи; удалили —
  опубликует и закрепит заново. «Обновить закреп» — сразу.
- **Заявки в чате**: каждая ордерная заявка публикуется в чат с кнопкой «Взять заявку в боте»; взяли или закрыли —
  сообщение меняется на «уже взята» / «закрыта», без кнопок.
- **Рассылка**: аудитория (все, продавцы с картами, на смене, ордерные мерчанты, чат) → любое сообщение (текст,
  фото, видео, файл) → предпросмотр ровно в том виде, как его увидят, → «Отправить». Идёт в фоне с лимитом
  Telegram, итог (доставлено / заблокировали бота / ошибки) приходит админу и в лог-чат. Одновременно — одна.
- **Рассылка заявок мерчантам**: ордерная заявка уходит сначала мерчантам с большим числом успешных сделок;
  досыл новым свободным мерчантам — раз в 20 с.

**Инлайн-поиск.** «Мои сделки» и «История операций» открывают поиск прямо в строке ввода (`@бот сделки …`):
фильтр по `#номеру`, сумме, статусу («спор», «завершена»), «покупка»/«продажа»; по операциям — по типу. Выбор
карточки отправляет `/deal N` или `/op N` через бота: это сообщение удаляется, а текущий экран превращается в
карточку сделки или операции. Нужно один раз включить инлайн-режим у бота: @BotFather → /setinline → бот →
подсказка, например «Поиск по сделкам…». Цвета кнопок: зелёная — купить/пополнить, красная — продать/вывести/
отменить, синяя — главное действие экрана.

**Сообщения.** Бот не удаляет свои старые сообщения — это история. Нажатие кнопки редактирует то сообщение, в
котором её нажали (оно становится текущим экраном). На команду или обычный текст приходит новый экран внизу.
Удаляется только ответ, набранный текстом на вопрос бота (сумма, номер карты, ФИО), а экран-вопрос при этом
редактируется на месте; файлы (чеки, доказательства) остаются в чате.

**Иконки.** Премиум-эмодзи — только в заголовке экрана и в строке результата (✅ / ⚠️); в фактах, шагах и
подзаголовках их нет (`ui.clean`). На кнопках иконка только у выделенных цветом главных действий.

## Команды
Команды: `/start` (`/menu`), `/buy`, `/sell`, `/wallet`, `/deals`, `/help`, `/support`, для админов `/admin` и
`/deal N`; в группах — `/help` (инструкции), `/team` (тимлид подключает чат);
меню команд ставится при запуске. Команда остаётся в чате, бот отвечает новым экраном внизу, у прошлого
экрана убираются кнопки. Любая команда завершает текущий шаг ввода: `/cancel` или опечатка никогда не
станет суммой, текстом обращения или доказательством — бот ответит «Неизвестная команда».
Ответ на любое сообщение появляется под ним, прошлый экран удаляется (кнопки кликов по-прежнему
редактируют экран на месте). Удаляются только ответы на вопросы бота (сумма, номер карты, ФИО, чек) и только
если они обработаны; обычный текст и команды не удаляются.
Обновления одного пользователя обрабатываются строго по очереди (`bot/storage.py: UserIsolation`): команда и
сообщение, отправленные одновременно, не гоняются за экран и состояние. Если обработчик упал, пользователь
всё равно получает ответ (алерт на кнопке или сообщение с «В меню»), шаг ввода сбрасывается.
Сообщения в группах (в т.ч. в лог-чате) игнорируются; кнопки «Открыть» в лог-чате работают.

## Истечение сделки и поздний чек
После истечения срока оплаты залог продавца ещё `late_hold_minutes` (30) остаётся замороженным: если
покупатель платил в последние минуты и пришлёт чек, сделка вернётся продавцу на проверку, а продавец не
сможет за это время вывести эти USDT. Потом залог освобождается автоматически. Чек после этого (до
`late_minutes`) примется, только если у продавца снова есть средства, иначе уходит админам.

## Чеки
По умолчанию только PDF; бот проверяет сигнатуру `%PDF`, переименованные файлы не принимаются.
`receipt_images=1` разрешает фото и скриншоты (их проще подделать — продавец всё равно сверяет поступление).

## Лог-чат: ветки и живые карточки
Включите в группе **Темы** (Настройки группы → Темы), добавьте бота админом с правом «Управление темами» и
напишите в группе (в любой ветке, например General) **`/setts`** — только от администратора бота. Бот запомнит
эту группу как лог-чат (`LOG_CHAT_ID` в .env менять не нужно), создаст все ветки, положит в каждую описание и
ответит списком; повторный `/setts` ничего не дублирует. Если тем нет или прав не хватает — бот ответит, что
включить. Ветки: 📝 Заявки на вход, ⚠️ Требует внимания, 📊 Статистика, 💱 Сделки, 🧾 Ордерные
реквизиты (с баланса), 🟣 Bybit-ордера, 🧑‍💻 Операторы и долги, 🫂 Команды и тимлиды, 📥 Пополнения, 📤 Выводы, 🔑 API,
🤝 Ордерные мерчанты, 👤 Пользователи, 💳 Карты, ✏️ Корректировки, 💬 Обращения, 👥 Чат и рассылки, ⚙️ Сервис (id веток хранятся в БД; удалённую ветку бот
создаст заново).
У каждой операции (сделка, вывод, пополнение, заявка на API, анкета мерчанта…) — **одна карточка** в своей
ветке: цветной статус (🟡 в процессе, 🟢 успешно, 🟠 нужно внимание, 🔴 ошибка/отказ, ⚪️ отменено), затем
**каждый факт отдельным пунктом «•»** — люди как `@username · имя · id` (покупатель, мерчант, оператор, админ), суммы,
курс и процент, доход площадки, реквизиты, способ и сеть, — и блок «История» с последними событиями.
В «Требует внимания» дублируется заголовок, кто и сколько, и что случилось — по пункту на строку. При смене статуса карточка **редактируется** (тихо), а всё, что требует админа
(спор, отказ xRocket, вывод «unknown», новая анкета и т. п.), дополнительно приходит в ветку «Требует внимания»
со звуком. Если чат без тем (или у бота нет права), всё идёт в общий чат: рядовые шаги правят карточку, а при
проблеме свежая карточка публикуется внизу, старая помечается «обновлено ниже».

## Лог-чат: что попадает
`log_all=1` (по умолчанию) — в лог-чат идут все шаги: новый пользователь, открытие сделки, чек, завершение,
отмена, истечение, решение спора, пополнения, выводы, новые карты. Проблемы помечены «нужно внимание»:
отказ xRocket при выводе (например, пустой баланс приложения), вывод `unknown`, споры, поздний чек без
средств, недоставленные уведомления, спор без решения дольше 2 ч. `log_all=0` — только проблемы.
`LOG_THREAD_ID` — топик, если лог-чат форум. Перед выводом бот сверяет баланс приложения xRocket: если его
не хватает, пользователь ничего не теряет, админам приходит алерт.
Свой баланс администратор изменить не может: корректировку себе проводит другой администратор.

## Emoji
`EMOJI_MODE=premium` — custom emoji из каталога Zulut30 (`bot/emoji.py`). Telegram показывает их, только если
у владельца бота есть Telegram Premium (или у бота купленный на Fragment юзернейм); иначе клиенты видят
обычные fallback-эмодзи — отключить fallback в Telegram нельзя, он обязателен для тега `<tg-emoji>`.
`EMOJI_MODE=plain` — только обычные эмодзи; `EMOJI_MODE=none` — интерфейс полностью без эмодзи и иконок кнопок.
