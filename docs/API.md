# Strait Pay API

**Версия:** v1 · **Формат:** JSON (UTF-8) · **Аутентификация:** Bearer-токен

Strait Pay API позволяет вашему сервису принимать оплату в рублях и получать USDT. Вы открываете заказ на нужную
сумму, показываете покупателю реквизиты продавца (мерчанта Strait Pay), загружаете PDF-чек перевода и получаете
статус `success`. После этого USDT зачисляются на ваш баланс в Strait Pay — на тех же условиях, что и при обычной
покупке в боте. Вывести их можно в боте: «Кошелёк → Вывести» (чек xRocket или USDT на кошелёк в любой сети xRocket).

## 1. Как это работает

```
Ваш сервис                    Strait Pay                         Продавец (мерчант)
    │  POST /v1/orders  ───────▶  подбирает продавца,
    │                             замораживает его USDT
    │  ◀── реквизиты, сумма ──────
    │  показываете реквизиты покупателю; он переводит рубли
    │  POST /orders/{id}/receipt ─▶  чек уходит продавцу ────────▶  проверяет поступление
    │                                                              в банке и подтверждает
    │  ◀── webhook: success ──────  USDT зачислены на ваш баланс ◀──
```

* Реквизиты выдаёт продавец: карта или номер телефона для СБП, банк и ФИО получателя.
* Под каждый заказ продавец замораживает свои USDT (или реквизиты выдаёт оператор Strait Pay из Bybit-ордера
  мерчанта), поэтому зачисление после подтверждения гарантировано.
* Если продавец не подтверждает оплату, вы открываете спор. Решение принимает администрация Strait Pay.

## 2. Получение доступа

1. Откройте бота Strait Pay → **Strait Pay API** (или команда `/api`) → **Подать заявку**.
2. Заполните анкету: проект, ссылка, откуда приходят покупатели, ожидаемый оборот в месяц, пара слов о проекте.
3. Администрация рассматривает заявку, обычно в течение суток. Ответ придёт в чат с ботом. Если заявку отклонили,
   причина будет в сообщении, подать заново можно через 24 часа.
4. После одобрения в разделе API нажмите **Выпустить токен**. Токен показывается **один раз**: мы храним только его
   SHA-256-отпечаток. **Перевыпустить токен** — старый перестаёт работать сразу.
5. Там же задайте **вебхук** (URL вашего сервера) и возьмите **секрет вебхука** для проверки подписи.

В разделе API видны Base URL, лимиты и их использование, баланс, последние заказы и ссылка на эту документацию.

## 3. Основы: адрес, авторизация, формат

| | |
|---|---|
| Base URL | `https://api.<домен-strait-pay>/v1` — точный адрес показан в боте в разделе API |
| Документация | `GET /docs` (этот файл) |
| Авторизация | заголовок `Authorization: Bearer sp_live_…` |
| Тело запросов | `Content-Type: application/json`, кроме загрузки чека |
| Суммы | строки с десятичной точкой: `"10000"`, `"10000.50"`, `"94.000000"` |
| Время | ISO 8601 в UTC: `"2026-09-27T18:04:05Z"` |
| Валюты | рубли — `amount_rub` (до 2 знаков), USDT — `amount_usdt` (до 6 знаков) |

Вызывайте API **только со своего сервера**. Токен даёт доступ к вашему балансу — не передавайте его в браузер или
мобильное приложение.

```bash
curl https://api.<домен>/v1/me -H "Authorization: Bearer sp_live_XXXXXXXX"
```

## 4. Статусы заказа

| Статус | Что происходит | Что делать |
|---|---|---|
| `searching_requisites` | Готовой карты под сумму не было — заявку получили ордерные мерчанты (до `search_expires_at`) | Ждать; покупателю — «подбираем реквизиты» |
| `merchant_assigned` | Мерчант взял заявку и готовит реквизиты (или ссылку на свой Bybit-ордер) | Ждать |
| `requisites_check` | Strait Pay проверяет Bybit-ордер мерчанта и выдаёт его реквизиты | Ждать вебхук `awaiting_payment` |
| `awaiting_payment` | Заказ создан, в `requisites` реквизиты продавца, до `expires_at` ждём перевод | Показать покупателю реквизиты и **точную** сумму, затем загрузить чек |
| `verifying` | Чек у продавца, он проверяет поступление в банке | Ждать. После `dispute_available_at` можно открыть спор |
| `dispute` | Спор, решает администрация Strait Pay | Ждать решения; при необходимости написать в поддержку |
| `success` | Продавец подтвердил поступление, **USDT зачислены на ваш баланс** | Выдать товар или услугу покупателю |
| `cancelled` | Заказ отменён: вами, администрацией или спор решён в пользу продавца | Покупателю не переводить деньги по этим реквизитам |
| `expired` | Время на оплату вышло без чека | Если покупатель всё же оплатил, загрузите чек до `late_receipt_until` |

```
searching_requisites ──взял──▶ merchant_assigned ──реквизиты──────────────────────────▶ awaiting_payment
      │                           │  └─Bybit-ордер──▶ requisites_check ──реквизиты──▶ awaiting_payment
      │                           └─отказался / не успел──▶ searching_requisites    (ссылка отклонена ──▶ merchant_assigned)
      └─никто не взял / не проверили вовремя / cancel──▶ cancelled (close_reason no_merchant / buyer_cancel)

awaiting_payment ──receipt──▶ verifying ──продавец подтвердил──▶ success
      │  │                        │
      │  └─cancel──▶ cancelled    └─спор──▶ dispute ──решение──▶ success | cancelled
      └─время вышло──▶ expired ──поздний чек──▶ verifying
```

Статусы до реквизитов (`searching_requisites`, `merchant_assigned`, `requisites_check`) могут сменять друг друга
несколько раз: мерчант отказался — заявка снова в поиске. Показывайте покупателю «подбираем реквизиты» во всех трёх.

Итоговые статусы — `success` и `cancelled`. `expired` может смениться на `verifying`, если прислать чек до
`late_receipt_until`. Если продавец молчит слишком долго, спор открывается автоматически.

Каждый заказ также содержит подсказки для интерфейса:

| Поле | Значения |
|---|---|
| `next_action` | `wait` — ничего не делать; `pay_and_upload_receipt` — показать реквизиты, затем загрузить чек; `dispute_available` — продавец молчит, можно открыть спор; `upload_late_receipt` — время вышло, но чек ещё примут; `null` — заказ закрыт |
| `stage` | `{"step": 1–4, "of": 4, "title": "Подбор реквизитов" \| "Проверка реквизитов" \| "Оплата" \| "Проверка платежа" \| "Спор" \| "Готово" \| "Отменён" \| "Время вышло"}` — прогресс-бар |
| `stage_deadline` | до какого момента длится текущий этап (поиск, проверка, оплата) или `null` |

`close_reason` уточняет итог: `no_merchant` (ордерные реквизиты не нашлись или не были выданы вовремя), `confirmed`, `buyer_cancel`, `expired`, `admin_void`, `ban_void`, `dispute_buyer`,
`dispute_actual` (зачислено по фактической сумме), `dispute_seller`.

## 5. Деньги: курс, комиссия, зачисление

* `amount_usdt = amount_rub / rate × (1 − fee_percent / 100)`, округление вниз до 0,000001. Текущие курс и
  комиссия — `GET /v1/rates`. Пример: 10 000 ₽ по курсу 100 с комиссией 6 % → **94 USDT**.
* Условия фиксируются в момент создания заказа (`rate`, `fee_percent` в ответе) и не меняются до его закрытия.
* У вашего подключения могут быть свои условия (курс и процент) — их задаёт администрация. Они одинаковы для всех
  заказов: и по статичным картам, и по ордерным реквизитам. `GET /v1/rates` всегда показывает именно ваши условия.
* При `success` сумма `amount_usdt` зачисляется на баланс владельца токена (`GET /v1/balance`). Если спор решён
  по фактически пришедшей сумме, `amount_rub` и `amount_usdt` в заказе пересчитываются.
* Вывод — в боте: USDT на ваш адрес в любой сети xRocket (TON, TRC-20, ERC-20, BEP-20, Solana; для бирж в TON — с memo) или чеком xRocket.

## 6. Методы

### GET /v1/me — аккаунт, лимиты, баланс

```json
{
  "project": "Shop One",
  "status": "active",
  "token_hint": "a1B2",
  "webhook_url": "https://shop.one/strait/webhook",
  "limits": {"min_order_rub": "500.00", "max_order_rub": "100000.00", "daily_rub": "1000000.00",
             "max_open_orders": 10, "requests_per_second": 5},
  "usage": {"open_orders": 2, "today_rub": "35000.00"},
  "balance": {"available_usdt": "412.500000", "frozen_usdt": "0.000000"}
}
```

### GET /v1/balance

```json
{"currency": "USDT", "available": "412.500000", "frozen": "0.000000"}
```

### GET /v1/rates

```json
{"pair": "RUB/USDT", "rate": "100", "fee_percent": "6",
 "example": {"amount_rub": "10000", "amount_usdt": "94.000000"}}
```

### GET /v1/liquidity — какие суммы можно заказать сейчас

Возвращает диапазоны сумм у продавцов, которые сейчас на смене, с учётом ваших лимитов. Личности продавцов не
раскрываются. Полезно показать покупателю доступные суммы до создания заказа.

```json
{"available": true, "offers": 3, "min_rub": "1000.00", "max_rub": "50000.00",
 "ranges": [{"min_rub": "1000.00", "max_rub": "21052.63", "bank": "Сбербанк", "type": "card"}],
 "order_requisites": {"available": true, "merchants": 4, "min_rub": "5000.00", "max_rub": "300000.00"}}
```

`order_requisites` — ордерные мерчанты, которые сейчас принимают заявки: в этом диапазоне заказ без готовой карты,
скорее всего, получит реквизиты (ответ 202).

### POST /v1/orders — открыть заказ

| Поле | Тип | Обязательно | |
|---|---|---|---|
| `amount_rub` | string | да | Сумма перевода, до 2 знаков после точки |
| `external_id` | string | нет | Ваш идентификатор заказа, 1–64 символа. **Ключ идемпотентности** |
| `bank` | string | нет | Только продавцы этого банка, например `"Сбербанк"` |
| `type` | string | нет | `"card"` — перевод по номеру карты, `"sbp"` — по телефону |
| `order_requisites` | bool | нет | По умолчанию `true`: если готовой карты под сумму нет, открыть заявку на ордерные реквизиты (ответ **202**). `false` — сразу `409 no_liquidity` |
| `sender_bank` | string | нет | Банк, с которого заплатит покупатель (2–40 символов) — мерчант подберёт реквизиты под него |

```bash
curl -X POST https://api.<домен>/v1/orders \
  -H "Authorization: Bearer sp_live_XXXX" -H "Content-Type: application/json" \
  -d '{"amount_rub": "10000", "external_id": "order-8841"}'
```

**201 Created**

```json
{
  "id": 1532,
  "external_id": "order-8841",
  "status": "awaiting_payment",
  "amount_rub": "10000.00",
  "amount_usdt": "94.000000",
  "rate": "100.00",
  "fee_percent": "6.000",
  "created_at": "2026-09-27T18:00:00Z",
  "expires_at": "2026-09-27T18:30:00Z",
  "receipt_uploaded_at": null,
  "closed_at": null,
  "close_reason": null,
  "requisites": {"bank": "Сбербанк", "type": "card", "number": "4111111111111111", "holder": "Иванов Иван"},
  "order_requisites": false,
  "next_action": "pay_and_upload_receipt",
  "stage": {"step": 2, "of": 4, "title": "Оплата"},
  "stage_deadline": "2026-09-27T18:30:00Z"
}
```

* Повторный запрос с тем же `external_id` не создаёт новый заказ, а возвращает существующий с кодом **200**.
  Смело повторяйте запрос при таймаутах сети.
* Strait Pay выбирает продавца с лучшей историей среди тех, кто может принять эту сумму. Если продавца забрал
  параллельный заказ, пробуем следующего.
* `requisites` возвращаются, пока заказ открыт (`awaiting_payment`, `verifying`, `dispute`), и скрываются после
  закрытия.
* Покупатель должен перевести **ровно** `amount_rub` **одним платежом** и **без комментария**.

**202 Accepted — ордерные реквизиты.** Если готовой карты под сумму нет, заказ создаётся в статусе
`searching_requisites`: заявку получают ордерные мерчанты Strait Pay, первый взявший выдаёт реквизиты специально под
этот заказ — сам (`merchant_assigned`) или через свой Bybit-ордер, который проверяет оператор Strait Pay
(`requisites_check`). `requisites` пока `null`, `order_requisites: true`, `search_expires_at` — срок текущего
этапа. Когда реквизиты выданы, придёт вебхук `awaiting_payment` (или опросите `GET /v1/orders/{id}`); время на
оплату — от 15 минут, точный срок в `expires_at`. Если никто не взял или реквизиты не выдали вовремя — `cancelled`
с `close_reason: "no_merchant"`. Отменить поиск — `POST /v1/orders/{id}/cancel`. Для вас все три статуса поиска
работают одинаково: курс и сумма в USDT уже зафиксированы.

Ошибки: `invalid_amount`, `invalid_external_id`, `invalid_type`, `invalid_field` (422), `amount_limit`, `daily_limit`,
`order_range` (422 — сумма вне диапазона ордерных реквизитов), `open_limit` (409), `no_liquidity` (409 — подходящих
продавцов нет и ордерные реквизиты выключены или недоступны, см. `/v1/liquidity`).

### GET /v1/orders/{id} — заказ

Ответ в том же формате, что и при создании. Дополнительные поля:
`dispute_available_at` — в статусе `verifying`, с какого момента можно открыть спор;
`late_receipt_until` — в статусе `expired`, до какого момента принимается поздний чек.

### GET /v1/orders/{id}/history — история статусов

Все смены статуса заказа по порядку — для поддержки и разбора спорных случаев.

```json
{"id": 1533, "status": "awaiting_payment",
 "history": [{"status": "searching_requisites", "at": "2026-09-27T18:00:00Z"},
             {"status": "merchant_assigned", "at": "2026-09-27T18:00:40Z"},
             {"status": "requisites_check", "at": "2026-09-27T18:02:10Z"},
             {"status": "awaiting_payment", "at": "2026-09-27T18:04:05Z"}]}
```

### GET /v1/orders — список

Параметры: `status` (любой статус из §4), `external_id`, `limit` (1–100, по умолчанию 50), `before_id` (для
пагинации: id последнего заказа предыдущей страницы). Сортировка — новые сверху.

```json
{"orders": [{"id": 1532, "status": "success", "...": "..."}]}
```

### POST /v1/orders/{id}/receipt — загрузить чек

Чек перевода из банковского приложения, **PDF** (фото или скриншот — только если это разрешено на площадке).
Максимальный размер — 10 МБ. Отправьте файл полем `file` в `multipart/form-data` или просто телом запроса.

```bash
curl -X POST https://api.<домен>/v1/orders/1532/receipt \
  -H "Authorization: Bearer sp_live_XXXX" -F "file=@receipt.pdf;type=application/pdf"
```

Ответ — заказ в статусе `verifying`. Принимается в статусах `awaiting_payment` и `expired` (до
`late_receipt_until`). Файлы проверяются по содержимому: переименованный текст или картинка с расширением .pdf не
пройдут. Если тот же файл уже загружали по другому заказу, продавец получит предупреждение.

Ошибки: `file_required`, `not_a_receipt` (422), `file_too_large` (413), `invalid_state`, `receipt_rejected` (409),
`owner_chat_unavailable` (409 — владелец токена должен открыть бота и нажать `/start`: копия каждого чека приходит
ему в чат).

### POST /v1/orders/{id}/cancel — отменить

В статусах `searching_requisites`, `merchant_assigned`, `requisites_check` и `awaiting_payment`, то есть **до**
перевода денег. Продавец получает уведомление, его средства
размораживаются. Ошибка: `invalid_state` (409).

### POST /v1/orders/{id}/dispute — открыть спор

Если продавец не подтверждает оплату, спор можно открыть в статусе `verifying` после `dispute_available_at`. Если
продавец молчит дольше, спор откроется автоматически. Ошибка: `dispute_not_available` (409).

### POST /v1/webhook/test — тестовый вебхук

Отправляет на ваш URL событие `{"type": "test"}` и возвращает результат:
`{"delivered": true, "result": "HTTP 200"}`.

## 7. Вебхуки

При каждой смене статуса заказа Strait Pay отправляет `POST` на ваш URL. Разрешены только адреса `https://` на
публичных серверах.

**Заголовки**

| | |
|---|---|
| `Content-Type` | `application/json` |
| `X-Strait-Event-Id` | номер события — используйте для защиты от повторной обработки |
| `X-Strait-Timestamp` | Unix-время отправки |
| `X-Strait-Signature` | `sha256=` + HMAC-SHA256(секрет вебхука, `timestamp + "." + тело`) в hex |

**Тело**

```json
{"id": 88, "type": "order.status", "status": "success", "created_at": "2026-09-27T18:12:40Z",
 "order": {"id": 1532, "external_id": "order-8841", "status": "success", "amount_rub": "10000.00",
           "amount_usdt": "94.000000", "...": "..."}}
```

* Ответьте **2xx** в течение 10 секунд. Любой другой ответ или таймаут — повтор через 10 с, 20 с, 40 с … (не реже
  раза в час), всего до 20 попыток, примерно сутки.
* События по одному заказу приходят в порядке изменений. `status` верхнего уровня — статус на момент события,
  `order` — актуальное состояние заказа при отправке.
* Обрабатывайте идемпотентно по `X-Strait-Event-Id` и проверяйте текущий статус через `GET /v1/orders/{id}`,
  прежде чем выдавать товар.

**Проверка подписи — Python**

```python
import hashlib, hmac, time

def verify(secret: str, headers: dict, body: bytes) -> bool:
    ts = headers["X-Strait-Timestamp"]
    if abs(time.time() - int(ts)) > 300:          # старше 5 минут — отклонить
        return False
    expected = "sha256=" + hmac.new(secret.encode(), ts.encode() + b"." + body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, headers["X-Strait-Signature"])
```

**Проверка подписи — Node.js**

```js
const crypto = require("crypto");
function verify(secret, headers, rawBody) {
  const ts = headers["x-strait-timestamp"];
  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return false;
  const expected = "sha256=" + crypto.createHmac("sha256", secret).update(`${ts}.${rawBody}`).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(headers["x-strait-signature"]));
}
```

Подпись считается по **сырому телу** запроса, до разбора JSON.

## 8. Ошибки

Любая ошибка возвращается в одном формате:

```json
{"error": {"code": "no_liquidity", "message": "No merchant can take this amount right now. See GET /v1/liquidity"}}
```

| HTTP | code | Причина |
|---|---|---|
| 400 | `invalid_json` | Тело — не JSON-объект |
| 401 | `unauthorized` | Нет токена, токен неверный или отозван |
| 403 | `suspended` | Доступ приостановлен администрацией |
| 404 | `not_found` | Заказа нет или он не ваш |
| 409 | `no_liquidity`, `open_limit`, `invalid_state`, `receipt_rejected`, `dispute_not_available`, `owner_chat_unavailable`, `webhook_not_set` | Действие невозможно в текущем состоянии |
| 413 | `file_too_large` | Чек больше 10 МБ |
| 422 | `invalid_amount`, `amount_limit`, `daily_limit`, `invalid_external_id`, `invalid_type`, `invalid_status`, `invalid_query`, `file_required`, `not_a_receipt` | Неверные данные |
| 429 | `rate_limited` | Превышен лимит запросов в секунду |
| 500 | `internal_error` | Ошибка на нашей стороне; операция не применена, повторите позже |

`message` написан для разработчика. Для логики используйте `code`.

## 9. Лимиты

Лимиты задаются администрацией для каждого клиента и видны в `GET /v1/me` и в боте.

| Лимит | По умолчанию | Ошибка |
|---|---|---|
| Сумма одного заказа | 500 – 100 000 ₽ | `amount_limit` |
| Оборот за сутки (с 00:00 МСК, открытые + успешные заказы) | 1 000 000 ₽ | `daily_limit` |
| Неоплаченных заказов одновременно | 10 | `open_limit` |
| Запросов в секунду | 5 (всплески до 10) | `rate_limited` |

Чтобы увеличить лимиты, напишите в поддержку из бота. Неоплаченные заказы занимают карты продавцов, поэтому
отменяйте заказы, которые покупатель бросил.

## 10. Интеграция по шагам

1. `GET /v1/me` — проверить токен и лимиты.
2. Покупатель выбирает сумму. При желании сначала `GET /v1/liquidity`.
3. `POST /v1/orders` с вашим `external_id` → показать `requisites`, **точную** `amount_rub` и таймер до `expires_at`.
4. Покупатель переводит деньги и загружает чек у вас → `POST /v1/orders/{id}/receipt`.
5. Ждать вебхук `success` (или опрашивать `GET /v1/orders/{id}` не чаще раза в 10 секунд) → выдать товар.
6. Обработать `cancelled` и `expired`, а при `verifying` дольше `dispute_available_at` — `POST …/dispute`.
7. Выводить накопленные USDT в боте: «Кошелёк → Вывести».

**Минимальный клиент на Python**

```python
import httpx

API = "https://api.<домен>/v1"
H = {"Authorization": "Bearer sp_live_XXXX"}

with httpx.Client(base_url=API, headers=H, timeout=20) as c:
    order = c.post("/orders", json={"amount_rub": "5000", "external_id": "cart-42"}).json()
    print(order["requisites"], order["amount_rub"], order["expires_at"])
    with open("receipt.pdf", "rb") as f:
        c.post(f"/orders/{order['id']}/receipt", files={"file": ("receipt.pdf", f, "application/pdf")})
    print(c.get(f"/orders/{order['id']}").json()["status"])  # verifying → success
```

## 11. Безопасность

* Храните токен в секретах сервера. При подозрении на утечку перевыпустите его в боте: старый перестанет работать
  сразу.
* Проверяйте подпись и время каждого вебхука и сверяйте статус через API перед выдачей товара.
* Не передавайте покупателю ничего, кроме реквизитов и суммы. Детали заказа — только на вашем сервере.
* Администрация может приостановить доступ (`suspended`) или отозвать токен. Вы получите уведомление в боте.

## 12. Для владельца площадки: запуск API

Переменные `.env`:

| | |
|---|---|
| `API_ENABLED=true` | включить HTTP-сервер (в том же процессе, что и бот) |
| `API_HOST=127.0.0.1`, `API_PORT=8080` | где слушать; наружу — только через HTTPS-прокси |
| `API_PUBLIC_URL=https://api.<домен>` | адрес, который видят клиенты (в боте, в `/` и в ссылке на документацию) |
| `API_RECEIPT_MB=10` | максимальный размер чека |

Пример Caddy (сам выпустит HTTPS-сертификат):

```
api.<домен> {
    reverse_proxy 127.0.0.1:8080
}
```

Модерация: «Админ-панель → API для сервисов». Там заявки (одобрить или отклонить с причиной) и клиенты: лимиты,
приостановка, отзыв токена, статистика заказов. О каждой новой заявке приходит алерт в лог-чат.
